# 재시험에서 발견한 공통 개선 후보

이번 시행 중 제품은 수정하지 않았다. 다음은 원인 확정과 구분한 후속 후보이며 사이트별 예외 규칙을 제안하지 않는다. 최종 정량 결과는 report.ko.md와 results-live.json을 따른다.

## 1. 실행 계약을 처음부터 올바르게 요청하게 만들기

- Amazon, Walmart, eBay, Best Buy 등에서 invalid_task/invalid_goal이 반복됐다. 실제 입력에는 steps 대신 actions, 잘못된 follow 위치, 허용 상한을 넘는 limit 등이 있었다.
- 스킬의 대표 예시를 실제 전체 입력 봉투와 일치시키고, 검증 오류에 필드 경로·허용 값·최소 올바른 형태를 반환하는 방안을 검토한다. 설명을 계속 덧붙이는 방식보다 예시와 검증기의 단일 계약이 우선이다.
- 요청이 거부된 횟수, 오류 후 정상 요청까지의 호출/시간을 측정한다. 실행되지 않은 오류와 실행 결과 불명을 구분한다.

## 2. 모드 전환을 반복 실행으로 오해하지 않게 만들기

- Google과 Expedia는 자동/수동 전환의 원인을 최종 headed 화면 상태로 오해하고 관찰 없이 종료했다. Walmart는 이미 headed인데 reveal을 반복했다. Best Buy의 수동 전환은 접근 제한이 입증되지 않았다.
- 전환 응답은 이전 실패 원인, 현재 모드, 현재 사용 가능한 세션, 현재 관찰 여부를 명확히 구분해야 한다. 이미 headed인 reveal의 재시작 비용과 멱등성도 검토한다.
- Wikipedia008은 detached-element 오류만으로 자동 전환됐다. Weather는 사이트 접속 전 Chrome 시작 실패 때문에 자동 전환됐다. 접근 제한 폴백과 일반 실행/시작 오류 정책을 구분해야 한다. 이는 단순히 Luna 프롬프트를 더 엄격하게 만드는 것으로 해결되지 않는다.
- 이전 변경을 자동 재실행하지 않는다. 다음 사이트는 독립 headless라는 시험 규칙을 유지한다.

## 3. 작은 출력 경로에서 대형 출력으로 새는 우회 경로

- Amazon010의 명시적 snapshot --format json은 stdout 약1.9MB를 만들었다. 전체 출력과 세션에 실제 전달된 잘린 도구 출력은 다른 지표다.
- 기본 경로와 상세 경로의 예산·페이징·접기 계약을 통일하고, 형식 선택만으로 전체 관찰 그래프가 노출되는지 점검한다. 필요한 정보의 정확한 부분 조회가 우선이며 본문을 다시 무조건 제거하는 해결책은 피한다.

## 4. 입력 후 읽을 대상을 UI 전환에 맞추기

- Walmart의 검색 입력/제출 후 follow가 닫힌 자동완성 범위에 붙어 not_ready가 됐다. 이후 실제 로봇 확인 페이지도 나타났으므로 이 문제만 해결하면 검색이 성공한다고 말할 수 없다.
- 열린 관계 대상, 닫힌 대상, 문서 이동, 새 세션을 구분해 명시적으로 요청한 후속 읽기를 현재 유효 범위에 연결하는 일반 계약을 검토한다. 임의의 비슷한 대상을 클릭하지 않는다.

## 5. 빈 결과와 실제 화면 미렌더링 구별

- Best Buy는 검색/브랜드까지 확인했지만 제품을 못 찾았다. 스크린샷 명령은 했어도 Luna가 이미지를 열어 보지 않았다. root가 종료 후 본 해당 스크린샷의 주요 상품 행은 빈 상태였다.
- 같은 zero-match를 되풀이하기 전에 목표 범위가 수집됐는지, 빈 것인지, 아직 렌더링되지 않았는지를 구분할 최소 근거가 필요하다. 이미지 경로 반환은 모델이 이미지를 봤다는 뜻이 아니다.
- 원인은 특정 사이트라고 단정할 수 없고, 페이지 전체에 제품이 없었다고 확대할 수도 없다.

## 6. 클릭 완료와 요청 조건 적용 구분

- Booking의 날짜 클릭과 Search는 완료됐지만 최종 도시 목록의 날짜는 비어 있었다. 기본 1박 가격은 요청한 2박/무료 취소 가격이 아니다.
- 매 클릭마다 전체 검증을 추가하기보다 최종 제출 전후의 관련 폼 값·URL·현재 안내를 작은 범위로 함께 반환하는 방안을 검토한다. 실패 지점의 일반 전환 증거를 확보한 뒤 원인을 정한다.

## 7. 입력과 Enter 사이의 DOM 교체

- Wikipedia008/011에서 fill 뒤 동일 핸들 Enter가 detached-element로 실패했다. 두 번 모두 outcome_unknown이었고, 최종적으로 관찰된 자동완성 항목을 선택해 진행했다.
- 동일 핸들 보존만으로 SPA 입력이 항상 안전해지는 것은 아니다. 값 입력과 제출의 실행 상태를 분리해 알려 주고, 입력이 적용된 상태에서 실패한 제출을 어떻게 재관찰할지 계약을 검토한다. 새로 보이는 유사 입력에 Enter를 자동 대입하는 해결은 피한다.
- Weather014/016에서는 오래된 More 참조를 반복했고, 새 find 결과로 전환한 뒤 성공했다. 현재 범위에서 아직 유효한 정보와 재관찰이 필요한 정보의 구분이 필요하다.

## 평가 원칙

성공률만 보지 않는다. 형식 오류 복구, 반복된 빈 조회, 불필요한 전환, 실제 전달량, 총 소요시간을 함께 본다. 한 사이트 한 번의 결과로 성능 향상이나 회귀 원인을 확정하지 않는다. 관찰 내용은 root 감사와 원시 명령 파일로 검증하고 에이전트의 어려움 없음 자체를 증거로 쓰지 않는다.
