# Airbnb: 현재 프로젝트 HB와 로컬 browser-use 비교

작성: 2026-10-16, GPT-6 Codex. 두 실행 모두 gpt-6-luna, medium, 새 에이전트 문맥, headed. 동시에 실행하지 않았다. 학습·사이트 자산화 없음.

## 과업과 판정

런던, 2027-01-05~08, 성인 2명, 1박 100,000원 이상으로 검색·필터 적용까지. 예약·결제 없음.

실제 가격 패널의 문구는 `Trip price, includes all fees`였다. 따라서 두 최종 결과 모두 **수수료 포함 3박 총액 최소 300,000원, 평균 박당 최소 100,000원**이다. 매일 개별 요금이 각각 100,000원 이상임을 보장하는 필터라고 주장하지 않는다.

## 수치

## 실제 과정: HB

- 프로젝트의 SKILL과 기록 launcher 사용. 실행 중 제품/SKILL 변경 없음. 사전 해시는 `source-provenance.json`에 있다.
- Where 입력과 London 자동완성 선택 후, 부가 가격 설명 팝업이 달력 탐색을 방해했다. 오래된 Close 참조 거부 뒤 현재 달력을 다시 관찰했다.
- 날짜 후보를 월 소속과 실제 라벨로 구별해 1월 5·8일 선택. 성인 증가를 두 번 수행하고 검색했다.
- `run`을 한 번 시도했으나 follow.fields에 허용되지 않은 `role`을 넣어 실행 전 거부됐다. 이후 대부분 단일 명령으로 진행해 연속 액션 장점을 활용하지 못했다.
- 체크아웃 날짜와 Show places에서 위험도 확인 요구가 각각 한 번 발생했다. 사용자가 승인한 검색 작업인데 추가 호출이 생겼다. 사이트별 예외로 우회하지 않았다.
- 가격 범위 조회에서 실제 내부 스크롤 소유자 범위를 따라가 Minimum 입력을 찾았다. 작은 controls/state가 조작 진입점에는 도움이 됐다.
- 그러나 `Trip price, includes all fees`는 본문에 있었고 첫 판단에는 쓰이지 않았다. 루나는 100,000을 입력한 후 박당 조건 성공이라고 보고했다. root가 단위를 다시 확인하게 한 뒤 총액 기준 오해를 인정했고, 별도 요청으로 300,000을 적용했다.
- 근거: private command #26 검색조건, #33 첫 입력, #35 첫 적용, #41 단위 문구, #47 보정 입력, #49 보정 적용, #52 단위·300000 재확인.

## 실제 과정: browser-use

- `D:/APPs/browser-use/.venv/Lib/site-packages/browser_use/skills/browser-use/SKILL.md` 직접 사용. browser-use 0.13.11, browser-harness 0.1.13. 스킬 SHA-256: `FEE8F320D0BDCAD3695393663B5DEFA6E5FC1E22FF7AC6FFB6F04F6997B93C36`.
- 로컬 CLI와 CDP helper 경로다. browser-use의 별도 자율 Agent API와 비교한 실험은 아니다. ChromeManager는 별도 headed 브라우저 준비·종료에만 썼고 웹 관찰·조작은 browser-use helper로 했다.
- 첫 호출에서 관찰하지 않은 검색 URL을 날짜·인원과 함께 조립했다. root가 동일한 UI 과업이 아니라고 지적해 #7부터 같은 탭에서 홈페이지로 돌아갔다. 초기 6호출을 지우지 않았다.
- 실제 London 제안 항목 좌표를 찾아 선택했다. 달력에서는 월 이동 좌표를 반복 사용했고, 예상한 `January 5`/`January 8` 이름 검색이 비었다. 실제 숫자 버튼의 aria-label과 좌표를 조회해 월을 구별했다.
- 체크아웃 후 Who 좌표가 바로 통하지 않아 버튼 좌표와 본문을 다시 읽었다. 이후 성인 2명으로 검색했다. #28 URL에서 날짜·adults=2 확인.
- #30의 약 1.1KB 본문 발췌에 `Price range`, `Trip price, includes all fees`, Minimum/Maximum이 함께 있었다. root가 가격 해법을 알려주지 않았으며 루나가 총액 300,000을 선택했다.
- Show places를 button/role=button으로 좁혀 찾지 못했다. 실제 텍스트가 있는 다른 요소를 조회해 좌표를 얻은 뒤 적용했다. 인용 오류로 Python SyntaxError 1회도 발생했다(#37, 실행 전).
- #36의 생성 URL에서 price_min=300000, price_filter_num_nights=3, 날짜·인원 보존 확인. #38의 본문에서 London, Jan 5–8 2027, 2 guests, ₩300,000+ 칩 확인. 마지막 클릭은 필터 패널을 다시 열지 못했지만, 가격 단위 근거는 이미 #30에서 확인했다.
- 전체 helper 기록은 클릭17, fill3, js45, cdp1, new_tab1, goto_url1, page_info4, wait_for_load4. 한 CLI 안 여러 helper가 가능하므로 HB CLI 수와 helper 수를 직접 비교하지 않는다.

## 이번에 얻은 개선 근거

1. 최소 출력은 단순한 글자 절약이 아니다. 입력값과 그 단위·설명은 같은 좁은 문맥 안에서 함께 전달해야 한다. HB는 입력을 찾았지만 단위가 빠져 더 큰 감사·수정 비용이 들었다. 특정 가격 문구를 하드코딩하는 대신 label/description/같은 경계의 원문을 보존하는 일반적 방법이 필요하다.
2. browser-use는 반환 구조가 단순하고 관찰+조작을 한 Python 호출 안 묶을 수 있었다. 다만 넓은 innerText/AX 출력도 썼고, 좌표 재탐색·예상 role 오류가 있었다. 좌표 방식만으로 우위를 단정하지 않는다.
3. HB의 follow 오류는 새 필드가 부족해서가 아니라 명령 교정 정보가 실제 HTTP 응답에서 누락된 문제도 있었다. 실험 뒤 `invalid_task`/`invalid_follow`의 private validation을 기존 invalid_goal과 같은 경계로 전달하도록 보완했다.
4. HB의 `display:contents` 경계가 자기 box가 없다는 이유로 자손의 현재 값까지 누락하던 문제를 사이트 없는 fixture로 재현했다. 실험 뒤 가시 자손 순회를 보존하도록 수정했다. 숨긴 자손은 계속 제외한다. 두 실전 결과에 이 사후 수정을 소급 적용하지 않는다.

새로운 사이트별 실행 예외를 추가하거나 browser-use를 수정하지 않았다. 원시 입력·응답·결과는 각각 `.runtime/work-surface-luna-airbnb-2026-10-16/airbnb/` 및 `.runtime/browseruse-airbnb-2026-10-16/`에 보관한다. 외부 공유용 문서에는 추적 URL 전체를 싣지 않는다. 전용 브라우저/daemon은 실험 뒤 종료했다.
