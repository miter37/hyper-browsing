# Airbnb 실전 HWM 출력량 점검

작성: 2026-10-15 09:25 KST · GPT-6 Codex

## 결론

현재 기본 출력은 과하다. 본문·소속·상태를 보존하는 방향은 유효하지만, 접힘 안내·링크 색인·반복 구조 설명과 공통 속성이 본문에 버금가는 양으로 반복된다. 문법을 버리거나 본문을 먼저 자르기보다 이 전달 비용부터 줄여야 한다.

저장한 실제 HWM 21개에서 공통 속성을 명시적 템플릿으로 묶는 분석용 변환을 실시했다. 합계 1,627,709 → 1,245,064 bytes, **23.5% 감소**. o200k_base 대리 토큰은 534,799 → 411,834, **23.0% 감소**했다. 모든 메시지의 전체 파싱 데이터 및 정규 직렬화가 원본과 정확히 일치하도록 복원 검증했다. 이 템플릿 문법은 제품에 도입하지 않았고 실제 LLM 이해도·응답 속도 개선도 검증하지 않았다. 작은 list 출력은 바이트가 줄어도 대리 토큰이 1개 늘었다. 바이트 절감과 토큰 절감은 동일하지 않다.

## 실전 수행과 범위

- 프로젝트 루트 SKILL.md를 읽고 `D:/APPs/hyper-browsing/scripts/launcher.mjs webctl`만 사용했다. 설치된 다른 스킬이나 브라우저 도구를 사용하지 않았다.
- 전용 데몬·프로필, headless=true, en-US, 1440×900, learningDisabled=true. 헤드리스 접근 성공으로 headed 전환은 필요하지 않았다.
- Airbnb 홈 → New York 입력 → 자동완성의 New York City 선택 → 2026-10-20~23 → 성인 2명 → 검색 → Filters → Wifi 선택 → 결과에 적용 → 목록 3개 확인.
- 날짜·인원·amenities[]=4를 실제 URL에서 확인했다. 필터 선택 상태와 결과 카드의 내용도 관찰했다. 예약·로그인·결제는 하지 않았다.
- 명령 26회: open 2(최초 환경 실패 포함), snapshot 7, fill 1, click 12, browser status 1, list 1, 저장 관찰 view 1, close 1. 클릭 12회 중 2회는 실행 전 확인 요구로 미실행, 나머지 10회 실행했다.
- 성공 open 시작부터 close까지 약 4분 25초. 모든 CLI 호출 소요시간 합계 약 45.9초(최초 실패 포함). 사이의 관찰·판단·측정 준비 시간이 있으므로 이를 브라우저 실행시간이나 모델 사고시간으로 혼동하면 안 된다.
- 첫 open 실패는 별도 프로필 디렉터리가 없어 Chrome 시작의 cwd가 성립하지 않은 환경 문제였다. 프로필 디렉터리 생성 후 성공했다. 사이트 차단 실패로 집계하지 않는다.
- 날짜 선택과 필터 적용 링크가 공통 위험 판정에 걸려 각각 not_started가 반환됐다. 현재 요청에 포함된 검색 조작임을 확인한 뒤 --confirm으로 진행했다. 사이트별 위험 규칙이나 CAPTCHA 처리를 바꾸지 않았다.
- 마지막에는 이번 실험 전용 세션·데몬·Chrome만 종료했다.

## 출력량

KB는 UTF-8 1,000 bytes. 원본은 실제 메시지를 파싱 후 정규 직렬화한 크기이며 터미널의 끝 개행 차이는 제외했다. 토큰은 js-tiktoken 1.0.21 / o200k_base 대리 측정이며 Luna 또는 실제 청구 토큰이 아니다.

| 홈 snapshot / 3 | 92.3 | 26,347 | 72.2 | 20,633 |
| 목적지 선택 후 달력 / 6 | 103.0 | 33,214 | 76.0 | 24,434 |
| 날짜 클릭 실행 전 거절 / 8 | 101.4 | 32,991 | 73.7 | 23,135 |

203.7KB 검색 결과의 구성은 노드 85.8KB, @gap 73.9KB(289줄), @links 38.5KB, 나머지 약 5.5KB다. **접힘·누락 안내와 링크 색인만 약 55.2%**다. 달력의 repeated-shapes 속성은 약 17.9KB, 변화 40줄은 약 11.2KB였다. 홈의 들여쓰기 공백만 약 9.7KB였으나 들여쓰기는 읽기와 소속 전달에 기여하므로 무조건 삭제할 대상으로 보지 않는다.

동일한 최종 관찰에서 현재 JSON의 contextGraph/collectionTiming/stateObservation을 뺀 제어 중심 투영은 36,892 bytes, HWM overview는 208,008 bytes로 약 5.64배였다. **동일 정보 비교가 아니다.** 제어 중심 투영에는 HWM의 본문·소속·추가 근거가 빠진다. 과거 엔진을 다시 실행한 결과도 아니다. 실제 전체 JSON 응답은 정본 그래프를 포함하여 약 1.54MB여서, JSON으로 바꾸는 것 자체가 해결책도 아니다.

`list --limit 3`은 약 5.2KB지만 18개 관찰 항목 중 3개만 다룬 별도 범위이고, 문단이 잘리고 title 필드가 비어 있는 결과였다. 전체 snapshot의 같은 정보를 5.2KB로 압축했다고 주장할 수 없다.

## 다이어트 후보: 사이트와 무관한 규칙

1. **범위 안내의 중복부터 줄인다.** @gap 공통 kind/reason/관찰 범위를 한 번 선언하고 각 parent·order·count·펼침 키를 보존하는 묶음 표현을 검토한다. folded/unobserved/unavailable/redacted와 부분 집계의 차이는 그대로 유지한다. 수백 줄을 단순 총계 하나로 바꾸지 않는다.
2. **링크 색인을 필요에 맞게 투영한다.** 기본 트리에는 각 링크의 목적지와 개별 실행 대상을 보존한다. 전역 목적지 색인은 같은 목적지의 중복이 있거나 질문 범위에 필요한 부분부터 보여주고, 나머지는 저장 관찰에서 조회 가능하도록 명시적으로 접는다. 목적지 개수 질문에는 완결성·정확한 범위·전체 색인이 필요하다. 같은 href라는 이유로 실행 대상을 합치지 않는다.
3. **공통 속성을 짧게 표현한다.** 이번 템플릿 실험은 복원 가능한 중복이 있다는 상한 근거다. 9~27개 등의 동적 템플릿을 매번 LLM에게 추적시키는 구현을 바로 채택하지 않는다. 고정 기본값·고정 속성 묶음·스코프 공유와 비교해 이해도 및 전체 조회 비용을 검증한다. 실행 ref의 epoch 안전성을 포기하거나 임의로 줄이지 않는다.
4. **구조 설명과 진단 상세는 계층화한다.** repeated-shapes의 상세 직렬화, 성능 phase/reference 진단은 full/inspect에 두고 기본 출력에는 짧은 구조·개수·완결성과 상세 경로를 둔다. 문서 교체·수집 불일치·부분 관찰 정보는 기본 출력에 남긴다. 이는 정보가 현재 뷰에서 빠지는 '상세 축약'이며 무손실 압축이라 부르지 않는다.
5. **조작 응답은 대상 주변과 변화가 중심이어야 한다.** 현재 query/focus에서도 수십 KB의 전역 안내가 남는다. 대상·폼/그룹·관련 상태·조상·새 팝업·문서 교체를 우선하고 무관한 전역 자료를 접는다. 미실행 not_started에도 약 101KB를 반환한 사례는 별도 우선 점검 대상이다. 미실행 시 기존 관찰 참조를 재사용하려면 '새 관찰 아님'을 명시해야 하며 페이지가 그대로라고 단정하지 않는다.
6. **변화의 공통 근거를 한 번만 쓴다.** 관찰 쌍·요청·attribution의 반복을 묶되 변경된 필드/값, 관찰별 별칭, unchanged의 필드 범위, incomparable 이유를 보존한다. 전체 변화는 같은 저장 자료에서 펼친다.

실험용 상세 축약은 repeated-shapes와 성능 phases/references만 제거하고 그 사실을 선언했다. 여기에 템플릿을 적용하면 홈 66.3KB, 달력 62.6KB, 검색 결과 145.6KB였다. **이 수치는 원본 전체 무손실 변환이 아니며**, 누락 상세가 필요하면 추가 조회 비용이 있다. 페이지 내용·상태를 먼저 삭제하는 방향의 실험은 하지 않았다.

## 다음 검증 기준

같은 저장 관찰로 가격-카드 소속, 날짜·인원 적용, 선택 그룹, 가림/스크롤 범위, 같은 목적지 링크 개수와 완결성을 묻는다. 원본과 축약 뷰의 정답·과잉 주장·추가 조회·총 토큰·시간을 함께 측정한다. 기본값 복원은 파서 왕복, 상세 접기는 실제 펼침 복구로 검증한다. 압축 후에도 50K 이상의 대리 토큰이 남는 결과가 있어 **23% 절감만으로 충분하다고 결론 내리지 않는다.**

이번에는 관찰·오프라인 분석과 기록만 수행했다. 제품 수집기·렌더러·실행 정책은 변경하지 않았다. 실전 1개 사이트의 관찰이므로 일반 사이트 전체의 성능 향상이나 LLM 혼동 감소는 아직 입증되지 않았다.

## 후속 구현: 2026-10-15 기본 출력 1차 축소

사용자의 "일단 줄여" 승인 후 제품의 기존 overview/focus 투영을 수정했다. 새로운 동적 템플릿 문법은 도입하지 않았다. 전역 목적지 색인은 최대 12개/항목 JSON 4096 bytes로 접고, 큰 roots 목록은 원래 형제 인덱스 범위·개수·펼침 경로로 대체했다. 반복 구조의 해시/단일 항목 그룹과 성능 진단 상세는 full에 남겼다. 문서 교체 등 수집 시점 근거는 기본 헤더에서 유지한다.

동일 최종 관찰을 현재 제품 렌더러와 저장 서비스에 넣어 재검증했다 (`measure-diet.mjs`, `diet-results.json`). 새 사이트 방문은 하지 않았다.

| 측정 | 수정 전 | 수정 후 | 감소 |
|---|---:|---:|---:|
| 기본 HWM | 208,008 bytes | 166,201 bytes | 20.1% |
| o200k_base 대리 토큰 | 69,006 | 54,032 | 21.7% |

350개 표시 노드의 주 문자열·부모/들여쓰기·관계·속성은 repeated-shapes 상세를 제외하고 동일했다. @state/@outline/@candidates도 동일했다. 접힌 링크 색인은 동일 저장 관찰에서 105개 목적지와 원래 refs를 모두 정확히 복구했다. 실행 대상은 합치지 않았다. @links의 index-complete는 보유 색인의 출력 완결성이고 기존 complete는 관찰 범위의 수집 완결성이다.

이 결과는 **상세 접기**이지 모든 상세가 즉시 들어 있는 무손실 메시지 압축이 아니다. 전체 색인 펼침은 52,838 bytes/18,493 대리 토큰을 추가하므로 기본 출력+전체 색인을 매번 요청하면 약 219KB/72,525 토큰으로 원본보다 커진다. 전체 링크 개수 질문과 같이 필요한 경우에만 펼쳐야 한다. LLM 이해도·청구량·실제 응답 속도 개선은 아직 주장하지 않는다. 기본 출력은 여전히 크며 후속 개선 여지는 남는다.

검증: 신규 2개 회귀가 수정 전 실패하는 것을 확인한 뒤 구현했다. 최종 `npm test` EXIT=0: 타입 검사 + HWM80/learning35/execution62/scenarios15/discovery46 = **238개 통과**. 회귀는 색인의 완결성 구분·중복 대상 유지·같은 관찰 복구·교차 세션 및 만료 거부·본문/상태/수집 시점 보존을 포함한다. `git diff --check`도 통과했다.

## 3개 사이트 × 3개 출력 실측

후속 요청으로 각 사이트를 헤드리스 Chrome에서 열었다. 동일 탭에서 Playwright body ariaSnapshot, 프로젝트 captureSnapshot, 현재 기본 HWM/overview를 순차 수집했다. 학습은 하지 않았다. 스크립트 `compare-three-sites.mjs`, 수치 `three-sites-results.json`, 원시 출력은 `.runtime/hwm-three-sites-20261015/`에 있다. 제품 코드는 변경하지 않았다.

| 페이지 | Playwright ariaSnapshot | HB HWM 제외 제어 JSON 투영 | HB 현재 HWM/overview |
|---|---:|---:|---:|
| Airbnb 뉴욕 검색 결과 | 32.3 KB | 46.2 KB | 167.6 KB |
| Wikipedia Apollo 11 | 419.3 KB | 37.7 KB | 149.3 KB |
| Hacker News 첫 페이지 | 40.6 KB | 34.0 KB | 90.7 KB |

KB는 전달 문자열 UTF-8 1,000 bytes. Playwright는 기본 출력이 정해져 있지 않으므로 ariaSnapshot을 비교 규칙으로 정했다. HB 제어 JSON은 현재 수집값에서 contextGraph/collectionTiming/stateObservation을 제외하고 CLI와 같은 pretty JSON({snapshot:...})으로 직렬화한 투영이다. 구버전 실행 또는 현재 --format json 전체 응답이 아니다. 공백 없는 JSON이면 이 열은 각각36.4/26.9/23.8KB다. HWM은 축소 수정이 반영된 기본 출력이다.

같은 정보를 동일 범위로 인코딩한 문법만의 비교가 아니다. Wikipedia의 ariaSnapshot은 전체 접근성 본문을 내보내지만 HB는 실행 요소160개, 정본 노드2000개 수집 상한과 overview 접기를 적용한다. Airbnb도 정본2000개에서 부분 수집이며 HN은 정본1218개에서 scan.complete=true였다. 제어 JSON에는 본문/소속 정보가 빠진다. Wikipedia의 감소를 전체 본문 무손실 절감으로, HWM 증가를 순수 문법 오버헤드로 해석하면 안 된다.

초기 Airbnb에서는 호텔 안내 dialog가 열려 ariaSnapshot이 팝업만372 bytes로 반환됐다. 최종 비교는 관찰한 유일한 dialog의 Close 버튼을 닫고 진행했다. 벤치마크의 일반 팝업 처리이며 제품에 사이트 예외를 추가하지 않았다. 최종 Airbnb aria는 HB 수집 전32,265/후32,067 bytes로0.6% 달랐다. Wikipedia/HN의 전후 aria는 동일했다. 같은 순간을 동결한 비교는 아니다. 실제 모델 청구량이나 이해도 차이를 새로 검증하지 않았다.
