## 1. 조사 범위와 한계

현재 프로젝트 스킬·launcher를 사용해 30개 사이트에 접속했다. eBay는 오류 화면, Reuters는 검증 화면이어서 정상 구조 평가에서 제외했다. 나머지 28개는 실제 내용을 관찰했다. 로그인·구매·예약·발송 없이 검색, 메뉴/달력 열기, 문서 이동, 스크롤 등으로 변화를 조사했다. 모든 사이트의 첫 화면 이미지를 실제로 열었고 주요 변화 화면도 확인했다.

총 63개 상태 묶음(첫 화면 30개와 후속 관찰 33개), CLI 226회, 스크린샷 63장이 남았다. 스크린샷 63장을 전부 읽었다는 뜻은 아니다. 첫 CLI부터 마지막 CLI는 18:50:55~19:02:52 KST였다. 도구 출력·코드 읽기·최종 분석 시간을 포함한 전체 연구 시간과는 다르다.

처음에는 headless였고 npm 진입 중 기존 자동 복구가 headed로 전환했다. 동일 브라우저에 독립 탭을 유지한 탐색 조사라 이후 일부 관찰은 headed다. 전환 전 참조를 쓴 arXiv/PyPI 조작은 stale_ref로 거부돼 새 관찰 후 확인한 역할/이름으로 다시 시도했다. 이를 사이트의 지도 실패나 수행 성공률로 계산하지 않았다. 차단 우회는 하지 않았다. 전용 브라우저·데몬을 정리했다.

비교를 위한 사용자 과업 성공률 실험이나 완성된 새 알고리즘의 A/B 실험은 아니다. 사이트별 적용 규칙을 만들지 않았다. 실험 하네스에 사이트 URL과 과업이 있는 것은 조사 대상 지정이며 제품 실행 로직이 아니다.

## 3. 코드까지 추적한 공통 원인

현재 [map.ts](../src/runtime/observation/map.ts)는 틀린 도구라기보다 'landmark 목록'에 가깝다. 사용자에게 필요한 작업 구역과 landmark는 겹치지만 같은 개념이 아니다.

1. **분할 후보가 좁다.** MAIN/ASIDE/NAV/HEADER/FOOTER와 제한된 ARIA 역할을 우선한다. section/form/list/grid/독립 스크롤열을 일관된 작업 구역으로 찾지 않는다. CSS 기하 폴백은 전체 후보가 2개 미만일 때만 body 직계 자식을 본다. header/footer가 이미 있으면 본문 내부의 분할은 보완되지 않는다. body 아래 wrapper 하나인 페이지도 충분히 내려가지 않는다.
2. **영역 이름과 내부 제목을 혼합한다.** ARIA 이름이 없으면 내부 첫 제목을 영역 이름으로 승격한다. 본문 전체의 첫 기사/첫 필터/첫 달이 전체 이름이 된다. Google 홈은 제목의 비렌더링 textContent까지 들어간 사례다.
3. **제목의 경계 규칙이 후보 규칙과 다르다.** nested header를 독립 landmark 후보에서 제외하면서 이름 계산에서는 여전히 header 아래 제목을 다른 영역의 제목으로 제외한다. 실제 DOM 조회로 Wikipedia H1과 W3C H1이 main 내부 header 아래 있음을 확인했다. 그래서 올바른 H1은 빠지고 뒤의 H2가 선택된다. 사이트를 구분하지 않고 수정 가능한 명확한 공통 결함이다.
4. **공간 표현이 너무 뭉친다.** `position` 한 값에 top/left/partial/above/below를 섞는다. 큰 세로 영역은 partial로만 남아 왼쪽/오른쪽이라는 정보가 사라진다. 가시성 검사도 크기와 display/visibility 중심이라 오프스크린과 가림을 구분해야 한다.
5. **고정 우선순위와 첫 8개가 현재 목적을 대신한다.** 위쪽/아래쪽 navigation이 첫 페이지를 차지하고, parent가 P10인데 P10은 첫 출력에 없는 경우도 있다. 패널별 대표 컨트롤2개·전체12개는 크기를 제한하지만 DOM 앞쪽 조절기만 대표가 될 수 있다.
6. **현재 viewport와 읽기 순서가 분리돼 있다.** 기존 Booking 세션에서 scroll 후 offset60/120이 계속 필터를 반환했다. 이번 Wikipedia/W3C 스크롤 관찰도 현재 보이는 절 대신 원래 이름과 위쪽 컨트롤을 돌려줬다. offset은 DOM 페이지 나누기이며 화면 이동의 대체물이 아니다.
7. **동적 작업면은 role만으로 못 잡는다.** React 검색, Booking/Airbnb 달력, IKEA/NASA 메뉴가 서로 다른 마크업을 쓴다. dialog/menu 역할이 없다고 새 작업면이 없는 것은 아니다. 반대로 내부 banner라는 이유로 전체 머리말로 해석해서도 안 된다.

## 4. 새 지도의 목표: 어디를 읽고 행동할지 바로 알게 한다

DOM 그래프를 하나 유지하고 필요한 정보를 투영한다. 별도 사이트 인식기나 거대한 시각 이해 시스템을 만들지 않는다. 다음 세 관점은 출력 모드/범위이며 서로 다른 브라우징 방식이 아니다.

- **전체 구조:** 주요 영역과 관계를 작게 안내한다. 본문을 싣지 않는다.
- **현재 화면:** 현재 viewport 또는 실제로 스크롤한 컨테이너 안의 구역·항목으로 읽는 진입점을 준다.
- **현재 작업면:** 방금 열린 메뉴/폼/달력/검색창을 국소 범위로 안내한다. 바깥 지도를 반복하지 않는다.

첫 두 관점을 혼동하지 않는 것이 중요하다. 전체 지도는 먼 아래쪽도 요약할 수 있지만 현재 화면 읽기는 지금 보이는 내용에 닿아야 한다. 화면에 보인다는 사실은 클릭 가능성·비가림 보장이 아니므로 hit-test 결과와 구분한다.

## 5. 사이트와 무관한 제작 규칙 제안

### 5.1 후보와 선택을 분리한다

후보 근거는 HTML/ARIA 영역, 폼 소유 관계, 실제 스크롤/클리핑 경계, 반복 항목의 공통 조상, 큰 형제 영역의 렌더링 배치다. 기하는 명시적 구조가 부족한 **그 영역 안에서** 보완하며 페이지 전체 landmark 개수로 켜고 끄지 않는다.

모든 flex/grid 자식을 패널로 만들지 않는다. 상품 카드20개는 목록 영역 하나와 항목20개다. 단일 wrapper는 제한된 깊이 안에서 내려가고, 큰 형제 구역에 내용/컨트롤이 독립적으로 있고 실제 화면 경계가 구별될 때 분할 후보로 삼는다. 표 기반/float/positioned 구조도 있으므로 flex/grid만 필수로 삼지 않는다. DOM 한 루트로 표현할 수 없는 기하 묶음은 DOM 부모라고 가장하지 않는다. 첫 구현은 실제 DOM 루트가 있는 보수적 분할로 제한한다.

후보마다 basis와 수집 범위를 남긴다. '왼쪽에 체크박스27개와 제목4개가 있는 구역'은 사실이다. 앱이 이를 '필터'라고 의미 분류할 필요는 없다. 의미 명칭은 실제 페이지의 명시 이름/제목이 있을 때만 원문으로 제시한다.

### 5.2 이름·제목·내용 표본을 분리한다

- 명시 ARIA 이름은 `name`과 출처로 보존한다.
- 내부 제목은 `headings`/`heading` 근거다. 첫 제목을 무조건 상위 name으로 바꾸지 않는다.
- 직접 연결된 제목이나 영역 자체의 대표 제목을 쓸 경우 결정적 소속/깊이 규칙과 파생 출처를 표시한다. nested header 배제 여부는 실제 보존 경계와 일치시킨다.
- 이름이 없으면 무명으로 두고 역할·위치·구조 개수로 선택하게 한다. 임의로 '결과 목록'을 붙이지 않는다.
- CSS/script 문자열과 숨김 텍스트를 보이는 제목으로 합치지 않는다. 접근성 이름/시각 원문은 출처가 다르면 따로 다룬다.

### 5.3 현재 화면과 스크롤 소유자를 주소에 포함한다

제안하는 현재 화면 읽기는 기존 DOM offset과 다른 범위다. viewport의 교차 범위 또는 사용자가 스크롤한 컨테이너의 clip 영역을 기준으로 한다. 스크롤 후 어떤 scroll owner의 위치가 바뀌었는지 반환하고, 현재 보이는 구역/반복 항목의 진입점을 제공한다. DOM 순서, 화면 순서, 겹침은 서로 구별한다.

기존 offset은 정해진 범위의 남은 내용을 이어 읽을 때만 유지한다. '본문을 보려고 스크롤했더니 왼쪽 필터부터 다시 읽음'은 정상 사용 흐름으로 남겨두지 않는다. 가상 목록은 전체 개수나 미관찰 항목을 추정하지 않고 현재 렌더링/관찰 범위를 알린다.

### 5.4 작업면은 조작과 연결해 찾는다

우선은 aria-controls/native popover 연결, expanded 변화, focus 이동, 실제 DOM 추가/노출 및 대상 주변의 컨트롤 집합을 사용한다. CSS 위치나 사각형 겹침만으로 모달을 확정하지 않는다. 이름이 없는 여러 후보라면 부분 관찰·모호함을 유지하고 좁은 이미지로 전환한다.

작업면의 DOM 소속과 화면 앞쪽에 떠 있는 관계는 별개다. portal로 body 아래 생성된 메뉴를 원래 버튼의 DOM 자식으로 바꾸지 않는다. 시각적 overlay 안의 header/footer도 페이지 전체의 banner/contentinfo와 구별한다. 기존 action-region/focus/recovery를 먼저 재사용한다.

### 5.5 작은 지도는 중요한 구역을 생략하지 않는 방식으로 작게 만든다

현재처럼 모든 nav를 일렬로 먼저8개 보여주기보다 주요 구역을 묶어 보여주고 세부 nav/하단은 접는다. 부모를 출력하거나 명시적인 접힘 경로를 줘 참조를 고아로 남기지 않는다. 큰 결과/본문 범위마다 읽을 경로를 한 개는 제공한다. 대표 컨트롤은 검색 입력/펼침 등 역할 근거와 현재 viewport를 사용하되 업무 의미를 추측하지 않는다.

최초 진입 응답 원문은 이번 조사에서 중앙값 약3KB, 최대약5.2KB였다. 이보다 큰 기본 출력을 당연시하지 않는다. 새 지도 기본 예산은 약2~4KB에서 시작해 현재와 동등한 근거 비교로 조정한다. 숫자는 검증 전 목표이며 hard limit으로 누락을 숨기지 않는다. 본문·정확한 좌표·선택지 전체는 필요한 범위에서 읽는다.

## 6. 언제 무엇을 다시 제공할 것인가

| 사건 | 자동 전달 | LLM의 추가 요청 |
|---|---|---|
| 처음 접속/기존 세션에 첫 연결 | 준비된 작은 전체 지도와 활성 작업면 | 목적에 맞는 영역만 읽기 |
| 새 문서/새 탭 | 해당 문서/탭의 새 지도 | 이전 지도/at을 새 문서에 쓰지 않음 |
| 같은 문서의 큰 구조 전환 | 새 주요 범위만 교체/추가 안내; 기존 지도 재사용 불가하면 작은 전체 지도 | 필요한 새 범위 읽기 |
| 메뉴/달력/검색창/드로어 열림 | 그 작업면의 제목·현재값·소수 컨트롤·읽기 경로 | 선택지가 부족할 때만 작업면 안 조회 |
| 작업면 닫힘 | 닫힘과 돌아갈 기존 범위 | 지도가 여전히 유효하면 재요청 없음 |
| 필터/정렬/탭 변경 | 대상 상태와 바뀐 목록/패널의 작은 요약 | 필요한 항목 내용 읽기 |
| 일반 입력·체크 변경 | 현재 값/선택 및 필요한 후속 관찰 | 전체 지도 요청 없음 |
| 문서/컨테이너 스크롤 | scroll owner·현재 위치 및 새로 보이는 주요 구역/항목 진입점 | 지금 보이는 내용이 필요하면 해당 범위 읽기 |
| 이미지/광고/숫자만 변경 | 현재 작업 판단에 필요하지 않으면 지도 재전송 없음 | 필요할 때만 조회 |
| 늦은 팝업/본문 준비 | 다음 명령/대기 완료 응답 시 바뀐 작업면/구조 알림 | 준비가 불명확하면 짧은 현재 관찰 |
| 앱 복구·headed 전환 | 기존 범위 유효성 철회, 실제 지도 제공 여부와 새 진입 경로 | 새 정보에서 재계획; 입력/쓰기 재전송 금지 |
| 잘못된 범위를 읽거나 길을 잃음 | 선택 범위와 현재 구조 차이를 드러냄 | 전체 덤프 대신 부모의 작은 지역 지도 요청 |

URL 변경은 신호 하나다. 같은 URL의 큰 변화는 갱신할 수 있고, fragment 이동/단순 query 변화가 전체 지도를 필요로 하는 것은 아니다. 구조 비교는 유지된 DOM identity, 명시 관계, 주요 범위 추가/제거/가시 상태·스크롤 경계로 계산하고, 의미 변화는 추정하지 않는다.

idle 상태에 비동기 토큰 출력을 계속 밀어 넣지 않는다. 에이전트가 요청한 조작/관찰의 응답 시점에 변화 요약을 붙인다. 실행기에 현재 목표와 follow가 있으면 그 범위를 우선한다. 새 지역 지도나 diff는 소비자가 실제 전달받은 지도 revision을 기준으로 해야 한다. 임의의 '최신 지도'를 암묵적으로 덮어쓰지 않는다.

처음 지도에서 늦은 작업면까지 완벽히 기다리는 정책은 피한다. 짧은 제한 안에서 구조 안정/초점/명시 상태를 확인하고 partial이면 그대로 표시한다. 모든 사이트에 긴 고정 대기를 추가하지 않는다.

## 7. 현재 프로젝트 수정 순서

1. **분명한 공통 결함부터:** map.ts의 이름 출처 분리, 실제 보존 경계와 제목 소속 규칙 일치, 비렌더링 제목 오염 방지. 대표 사례는 Wikipedia/W3C/Google이지만 회귀 fixture는 도메인 없는 로컬 HTML로 만든다.
2. **관찰 영역 분할:** 기존 명시 경계를 유지하며 그 안에서 큰 구조적 분기를 보완한다. PyPI/Best Buy/기존 Booking과 HN/Weather의 다른 구조로 같은 규칙의 적용/미적용 근거를 확인한다. CSS grid 하나만을 정답으로 삼지 않는다.
3. **현재 화면 읽기:** scroll owner·clip·뷰포트 범위와 현재 항목 진입점을 추가한다. map.ts, service.ts, outline.ts 및 read의 범위 계약을 함께 수정해야 한다. offset 의미를 조용히 바꾸지 않는다.
4. **작업면과 갱신 통합:** 기존 focus/recovery를 확장해 role 없는 노출면도 제한된 기계적 근거로 안내한다. 큰 구조 변화/국소 변화/값 변화를 나눠 지도 교체와 국소 응답을 선택한다. P번호 순서 변경을 동일성으로 해석하지 않는다.
5. **짧은 SKILL 유지:** 절차는 '첫 지도 → 받은 대상으로 행동 → 새 작업면/현재 화면의 필요한 부분 → 충분하면 종료'로 유지한다. 내용 질의와 조작 대상 질의는 짧은 한 문장·예시로 구별하고 상세 기술 계약은 COMMANDS에 둔다. 사이트별 지침과 예외 문구를 추가하지 않는다.

처음부터 전체 지도 시스템을 한 번에 교체하지 않는다. 기존 실행 계층과 참조 가드는 유지하고 관찰/주소/출력의 개선을 작은 묶음으로 검증한다. 새로운 ref 수명이나 임의 재매칭으로 복구를 해결하지 않는다.

## 8. 검증과 채택 기준

로컬 fixture: nested header H1, 무명 main의 좌우 열, header/footer만 있고 body-wrapper가 깊은 페이지, table 반복행, 카드 grid, 독립 scroll sidebar, portal menu, role 없는 calendar, shadow root 검색, 초기 지도 후 늦은 팝업, SPA 교체, 긴 페이지 scroll, 가상 목록 부분 관찰을 포함한다. 이름·현재값·본문은 바꿔도 구조가 같으면 동일 규칙이 작동해야 한다.

그다음 업종/마크업이 다른 실제 사이트에 같은 규칙을 적용한다. 개발에 사용한 사이트를 전부 검증 집합으로 재사용하지 말고 새 사이트를 별도로 남긴다. 이번에는 사전 분리된 blind holdout이 없었으므로 일반화 성능을 측정했다고 주장하지 않는다.

주요 지표는 원하는 범위까지의 추가 호출, 엉뚱한 영역에 소비한 bytes, 누락/과분할/잘못된 이름, 조작 후 작업면 첫 응답 적중, DOM offset 순회 횟수, 전체 과업시간·총 출력/이미지 비용이다. 지도 개수나 영역 탐지 수가 많아지는 것은 성공이 아니다. 가시성·비가림·실행가능성은 따로 검증한다.

새 구조가 없어도 정상인 화면에서는 기존보다 출력과 대기를 늘리지 않아야 한다. 이름이 불확실하면 무명으로 남기고 위치와 원문 표본을 제공한다. 분할이 불명확하면 기존 main/문서 범위를 유지하고 현재 화면/작업면의 작은 조회나 이미지를 B플랜으로 쓴다. 추측한 경계가 더 위험하면 나누지 않는다.

## 최종 판단

현재 지도에는 유용한 초기 안내·국소 복구가 있지만, landmark 목록을 작업 지도처럼 사용하는 공백이 있다. 가장 먼저 개선할 것은 HWM 기호나 프롬프트의 길이가 아니라 **영역의 경계, 이름의 소속, 현재 화면으로 읽는 주소, 변화의 전달 시점**이다. 이 네 가지를 같은 관찰 모델 안에서 고쳐야 특정 사이트 예외 없이 LLM의 탐색 낭비를 줄일 수 있다.
