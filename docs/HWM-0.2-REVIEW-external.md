## 1. 합의 과정(44분 상호 비평)에 대한 평가

### 잘한 점

**검증과 서술을 분리한 규율.** "수집했지만 안 보인 것(folded) / 안 한 것(unobserved) / 못 읽은 것(unavailable) / 숨긴 것(redacted)" — 누락의 4상태 정의 자체가 최고 수확이다. "관찰보다 강한 주장 금지"를 원칙으로만 두지 않고 자기 서술에도 적용했다(`target=_blank` ≠ 새 탭 생성, `href="#"` ≠ 이동 없음, `after=req7`은 인과 확정이 아님). 주장마다 `.runtime`의 원시 command-NNN.json 링크가 붙어 있어 반박이 가능했고, 그래서 상호 비평이 공회전하지 않았다.

**정정이 실제로 일어났다.** GPT-6의 수치 지적(16/30 원인 과장) → Claude가 원시 명령을 재분류해 "내용 읽기 19/32(60%)"로 자기 핵심 발견을 하향 정정한 흐름이 이상적이다. Claude의 15:09 참조 수명 정정(자기 주장을 코드 읽고 뒤집음)도 마찬가지. 이런 로그에서 드물게, 첫 결론이 고정되지 않았다.

**교차 검증이 작동했다.** daemon 재시작 시 ref 재사용 위험(`snapshot.ts:386-389`, `references.ts`)은 상대의 추상적 원칙("참조 수명 분리")이 실제 코드에서 구체적 취약점으로 확인된 사례로, 원칙 → 코드 → fixture 요구까지 이어진 가장 생산적인 한 수였다.

### 약한 점

- **근거의 비대칭.** GPT-6은 6개 사이트를 직접 검토하고 수치를 재계산했다고 주장하지만, Claude 쪽 사이트 기록(Wikipedia·Walmart·Expedia)은 "전달받은 것"으로만 취급된다. GPT-6이 Claude 수치를 재검증한 건 eval 수치 하나뿐이고, Claude도 GPT-6의 6개 사이트 근거를 재확인한 적은 없다. 합의의 상당 부분이 "각자 본 것을 상대가 믿어주는" 상태다.
- **검증이 전부 미래형.** 44분 동안 새 사이트 접속, 코드 변경, 실험은 0회였다. 합의된 계약 전체가 아직 가설 묶음이고, 특히 "들여쓰기 뷰가 포인터/평탄 뷰보다 낫다"는 핵심 명제 자체가 미측정이다.
- **문법 논의의 수렴 비용.** 속성 줄 표기, `@gap reason=budget`, 한 줄 다중 노드 등 자기 예시를 스스로 부수는 작업이 3~4라운드 반복됐다. 라운드당 수확이 줄어드는 diminishing returns 구간이 분명히 있었다.
- **모델 라벨의 신뢰성.** "Opus 5.5" "GPT-6" 자체 표기는 실제 모델과 무관할 수 있다. 내용 품질에는 영향이 없으나, "어떤 모델이 어떤 판단을 잘하는가"의 증거로는 이 라벨을 신뢰할 수 없다.

### 메타 관찰

이 프로세스가 작동한 이유는 두 기록이 **원시 증거에 고정된 반박 가능한 주장**을 생산했기 때문이다. 마지막 항목의 자기 한계 표시("이 기록은 설계 결정이며 제품 코드 변경이나 효과 검증 완료를 의미하지 않는다")가 로그 전체의 신뢰도를 올려줬다. 방법론 9/10, 현재 상태는 "잘 검증된 가설" 수준.

## 2. 합의 명세(HWM-0.2-consent.md)에 대한 평가

### 총평

"합의된 내용만 옮겼다"는 선언이 문서 자체에서 검증된다. 14장의 결정 기록 표가 핵심인데, 모든 결정이 "누가 언제 제안하고 누가 언제 수용했는가"의 감사 추적을 갖췄다. 합의 문서라기보다 합의의 *증거 문서*다.

### 강점

1. **추상 원칙이 판정 가능한 계약으로 번역됐다.**
   - `@change op="unchanged"`는 "그 필드에 한정" — Δ none 논쟁이 필드 단위 계약으로 착지.
   - `selected=null complete=false` → "선택 없음으로 확정하지 않는다" (9.4 fixture g8가 정확히 그 케이스).
   - `covered-by`는 `test="center"`를 반드시 쓰도록 강제 — 결과 강도를 바꾸는 한정을 숨기지 않음.
   - `attribution="observed-after"` ≠ 인과 확정.
2. **자기 반증이 fixture에 내장돼 있다.** 9.4 보조 fixture는 성공 사례가 아니라 함정 사례(그룹 일부만 관찰, 트리 안 @gap, 잘린 이름)다. 11.2 이해도 과제의 "판단 불가를 정답에 포함"과 짝을 이뤄, 검증 설계가 명세와 같은 논리를 쓴다.
3. **정직한 경계 표시.** 상태 헤더의 "구현·검증 아님" 선언, 11.3의 eval 수치를 "Claude 재분류, GPT-6 미재계산"으로 출처 표기, 12장 열린 항목에 결정 방법까지 명시, 13장 범위 밖에서 risk.ts 정책 교체 분리.
4. **Δ → `@change` 통일 결정은 옳다.** 비ASCII 기호의 Windows 콘솔 인코딩 위험은 이 프로젝트 실행 환경에서 실제 문제이고, "다른 레코드와 같은 @ 문법"은 7.1의 "짧게 만들려고 예외 문법을 추가하지 않는다"와 정확히 일치한다. 이 결정이 합의 과정 밖에서单方面으로 내려진 사실도 14장에 숨기지 않았다.

### 약점과 위험

**2.1 EBNF와 예시가 어긋나는 지점 (단계 0 파서 작성 시 충돌 지점)**

- 7.2는 "@gap을 해당 부모의 마지막으로 출력한 자식 바로 뒤에 둔다"고 하는데, 9.4 fixture에서는 `@gap gp1 parent="g4"`가 `g4 list` **뒤에** 나온다. g4는 n1의 자사고 gp1의 parent는 g4이므로, 규칙대로면 gp1은 g4 서브트리 안쪽 끝이어야 한다. fixture가 규칙보다 먼저 쓰였을 가능성이 높고, 파서·검증기 만들 때 첫 충돌이 여기서 날 것이다.
- `complete` 키가 두 뜻으로 쓰인다: `@state st1 complete=true`(레코드 완결성)와 `- g7 selected=["e40"] complete=true`(그룹 관찰 완결성). 블록 항목 속성과 레코드 속성에서 같은 키가 다른 의미를 갖는 것은 파서 계약에서 명시해야 할 애매함이다.
- 7.1의 `relation`은 종점이 단일 노드인데, 다대다 관계(`header-for` 제외)의 인라인 표기가 정의되지 않았다.

**2.2 "쌍방 합의"의 마지막 마일이 안 닫혔다.** 합의 당사자가 GPT-6인데 Δ → `@change` 결정과 문서 작성 자체가 Claude 쪽 단독이다. GPT-6이 15:11:59에 세운 규율("상대가 아직 승인하지 않은 내용을 합의된 것으로 표시하지 않는다")로 보면 이 문서는 아직 조건부 합의 상태다. 상태 라벨("쌍방 합의된 설계 명세")은 GPT-6 추인 전에는 과대하다.

**2.3 여전히 전부 가설이고, 그 고백이 11장에만 있다.** 문서 전반의 톤은 확정적인데 검증은 전부 미래형이다. "들여쓰기 뷰가 낫다"는 문서의 존재 이유 자체인 명제가 11.3 실험 1에 가서야 측정 대상으로 등장한다. 41% 문자 수 감소조차 "재계산 안 함" 표기가 11.3에만 있고 7장 예시들은 그 여운으로 쓰인다.

**2.4 구현 비용에 대한 침묵.** `text-source`/`name-source` 어휘, `identity="tracked-dom-node"`, `@links` 색인, `@outline` — 전부 수집기 변경이다. 4장은 코드 연결 지점을 인계안에 위임하고 12장은 비용을 열린 항목으로 뒀지만, 단계 0~1이 "직렬화·파서" 수준으로 보이는 것과 달리 실제로는 snapshot.ts·page-state.ts의 상당한 확장을 전제로 한다. 10장 완료 기준은 "무엇이 되면 되는가"만 있고 "얼마나 드는가"가 없다.

## 3. "이 아이디어는 잘 될까" — 확률 판단

### 구조적으로 확실히 이기는 부분

1. **"부재의 표시"만으로도 이미 이득이다.** 4상태 누락 구분은 LLM 실패의 고전적 원인("없다"와 "모른다"의 혼동)을 정면으로 고친다. 이 한 가지만 들어가도 환각성 조기 종료와 불필요한 재시도가 줄어드는 건 다른 분야 연구(SearchOS 실험에서 검색 실패를 명시적으로 표시했을 때 성능 상승)로도 지지된다. 성공 확률이 높다.
2. **소속 보존은 innerText fallback을 구조적으로 죽인다.** eval 대체율 16/30 기준선이 문제를 증명한다. 항목 안 본문 텍스트를 원문 순서로 넣는 것만 eval 이유 19건(내용 읽기)을 대체한다. 이건 문법까지 갈 필요 없는 수집 개선이고 확실히 먹힌다.
3. **산출물이 문법만이 아니라는 게 안전망이다.** graph 직렬화는 diff·검사·저장에 그 자체로 쓰이고, view는 프롬프트 텍스트다. LLM 성능이 기대에 못 미쳐도 정본 그래프는 남는다. 하방 리스크가 구조적으로 제한된 설계다.

### 회의적으로 보는 부분

1. **"문법이 좋으면 LLM이 덜 헤맨다"의 인과가 약하다.** 웹 접근성이라는 20년 자연 실험이 있다. 스크린리더 트리는 소속·관계·상태·누락을 이 명세와 거의 같은 방식으로 표현한다. 그런데도 스크린리더 사용자는 complex 웹에서 헤맨다. 원인은 표현이 아니라 웹 자체가 불완전하고 역동적이며 이벤트 드리븐이기 때문이다. 표현 개선의 상한은 LLM의 읽는 능력이 아니라 페이지가 사실에 대해 실제로 말하는 양이 정한다.
2. **정합성 비용이 과소평가돼 있다.** name-source 6종, text-source 5종, 부분 개수 JSON, identity 추적, 파생 개요, 색인 — 전부 수집기 변경이다. 이 프로젝트의 실패 기록 자체가 "복잡한 계약이 사례 누더기로 변질되는 과정"에 대한 경고로 가득했는데, 그 누더기가 수집기 쪽에 쌓일 위험이 있다. 결정성 계약은 동적 페이지·shadow DOM·재렌더링 앞에서 유지하기 비싸다.
3. **이 프로젝트의 LLM은 Claude다.** "판단 불가가 정상 정보"라는 계약이 실제 에이전트 루프에서 재관찰 남용이나 판단 보류로 이어지지 않는다는 실측이 0이다. 11.2를 통과해도 루프 행동은 별개 문제다.

### 층별 결론

| 축 | 판단 | 근거 |
| --- | --- | --- |
| 수집 개선(본문 보존, 누락 4상태, match 근거) | 잘 된다 | 현재 snapshot의 명백한 결함 수정. eval 대체율이 떨어질 게 거의 확실 |
| view 문법(들여쓰기 뷰, 기호 체계) | 조건부 | 11.3 실험 1에서 평탄 출력 대비 유의미한 이득이 나와야 살아남는다 |
| 전체 비전("LLM이 안 헤맨다") | 과대 약속 | 헤매는 것의 상당 부분은 표현이 아니라 웹과 모델의 본질적 성질 |

### 권장 실행 순서

명세 10장의 순서(계약 → 직렬화 → 수집)는 "설계로서 완벽한 산출물"을 전제로 한다. 불확실성 하에서는 가장 싸고 확률 높은 실험을 먼저 해야 한다.

1. 문법 전체를 먼저 만들지 말 것. 단계 0 파서·검증기는 11.1 검증용으로 최소한만.
2. **수집 개선 3개(본문 텍스트, 누락 4상태, match 근거)를 현재 평탄 출력에 먼저 얹어 실사용 실험.** 2~3주면 eval 대체율과 작업 성공률의 실제 숫자가 나온다.
3. 그 숫자가 긍정적이면 view 문법 실험(11.3 실험 1) — fixture 3개로 LLM 이해도 비교.
4. 부정적이면 문법은 버리고 graph 직렬화(diff/검사용)만 남긴다.

두 에이전트가 44분 동안 증명한 방법론 — 주장마다 원시 증거를 붙이고 가장 싼 검증부터 한다 — 을 그들의 구현 계획에도 적용하라는 것이 이 검토의 답이다.
