# HB 목표 중심 코어 설계 — 검토 초안

작성: 2026-10-15 — GPT-6 Codex

상태: 승인된 설계. 2026-10-15 목표 조회·조작 후 검증·짧은 조건부 계획의 첫 코어 구현을 완료했다. 구현 기록은 [개발 계획](plans/HB-goal-driven-core-implementation.md)에 있으며, 전체 과업 비용의 개선 폭은 별도 비교 평가 대상이다.

## 목표와 선택

LLM은 목적, 의미 판단, 선택과 예외 처리를 맡는다. HB는 현재 화면에서 필요한 사실을 찾고, 선택된 대상을 실행하고, 명시된 다음 조건을 확인한다. 확정 가능한 작은 단계는 한 호출에서 이어가고, 새로운 판단이 필요한 지점에만 제어를 돌려준다.

성공 기준은 같은 목표를 정확히 끝내는 데 든 전체 시간과 비용이다. RPC 수, 문자열 길이, 로컬 실행 시간만으로 성공을 선언하지 않는다. 관련 정보가 부족하면 더 주되, 이미 받은 유효한 정보와 무관한 구조는 반복하지 않는다.

검토한 세 방향:

| 방향 | 장점 | 한계 | 선택 |
|---|---|---|---|
| 기존 명령에 find 옵션만 추가 | 빠른 도입 | 매 클릭의 모델 왕복, 이름 재해석, 대기 단절이 남음 | 최종 구조로는 부족 |
| 목표·관찰·실행·전환 확인을 묶은 코어 | 모델 판단과 확정 실행의 경계가 명확하며 기존 안전장치 공유 가능 | 공통 대상 모델과 조정 계층이 필요 | 권장 |
| 긴 범용 자율 러너·사이트별 스크립트 중심 | 성공 경로에서는 호출이 적음 | 새로운 UI·팝업·차단에서 복구가 어렵고 의미 판단까지 앱에 들어오기 쉬움 | 기본 방식으로 채택하지 않음 |

새 코어를 만들되 Playwright와 검증된 입력·참조·요청 추적은 사용한다. 현재 서비스의 메서드 배치를 유지하기 위해 새 구조를 비틀지 않는다. 임시 goal-follow DOM 검색기를 정식 엔진으로 옮기지 않는다.

## 기본 루프

`목표·조건 수신 → 필요한 범위 관찰 → 후보와 근거 연결 → 선택 조건 충족 시 실행 → 관련 상태 전환 확인 → 다음 확정 단계 또는 판단 요청`

- 최초 목표가 명확하면 목표 후보와 작은 위치·소속을 먼저 준다. 무조건 패널 지도부터 읽게 하지 않는다.
- 목표가 아직 넓으면 작은 패널 지도를 준다. 전체 컨트롤·본문·HWM을 기본으로 붙이지 않는다.
- 목표는 실행할 현재 대상과 행동 뒤 찾을 다음 대상을 구분한다. 하나의 검색어를 두 역할에 암묵적으로 재사용하지 않는다.
- 자연어 목적만 던지고 엔진이 의미를 추측해 실행하는 구조는 만들지 않는다. LLM이 검색 조건과 허용 행동·검증 조건을 선언한다.
- 목표·계획은 현재 과업의 임시 상태다. 사이트 학습·영구 러너 등록과 연결하지 않는다.

## 네 가지 핵심 책임

### 1. 대상과 근거를 함께 찾는 관찰

기존 관찰 기능과 목표 조회가 동일한 브라우저 수집 함수·이름 출처·참조 등록기를 사용하게 한다. HWM 그래프 전체 생성은 이 경로의 전제 조건이 아니다.

후보의 최소 계약:

- 실제 발급 ref, 문서 범위, 관찰 시점과 수집 범위.
- accessible-name과 보이는 text를 구분하고 일치 필드·일치 구간·출처를 표시.
- placeholder, 현재 value, href를 이름으로 합치지 않음.
- 역할·관련 상태·현재 영역·필요한 항목/행/폼 소속.
- 필요한 경우에만 주변 원문과 뷰포트 위치. 원시 좌표·전체 조상 경로는 기본 생략.
- 부분 수집·잘림·필드 미수집·마스킹을 0건/없음과 구분.

질의는 이름뿐 아니라 원문·href·값을 대상으로 할 수 있다. 여러 대체어는 LLM이 명시한 문자열 집합이다. 엔진이 사이트별 사전이나 의미 분류기를 붙이지 않는다. 후보 정렬은 허용하되 상위 후보라는 이유로 실행하지 않는다. 짧은 계획의 자동 실행 조건은 선언 조건을 만족하는 유일한 후보여야 한다.

현재 열린 영역을 우선 검색하되 의도한 목표의 범위가 그 안인지 확인한다. 팝업 뒤 배경 요소를 함께 섞지 않는다. 메뉴가 포털로 렌더되어도 새 영역의 실제 노드를 추적한다. 범위 밖에서 못 찾은 것을 페이지 전체에 없다고 반환하지 않는다.

Maps처럼 accessible-name이 비어도 보이는 텍스트가 있는 대상을 지원한다. 사실을 합성 이름으로 승격하지 않고, text와 실제 조상 컨트롤의 관계를 연결해 그 컨트롤 ref를 반환한다.

### 2. 공통 실행

현재 executePrimitive를 기본 실행 경계로 삼는다. 클릭·입력·키·선택은 조회에서 얻은 실제 ref로 연결하고 실행 직전 수명·대상 가드를 확인한다. 이름으로 다시 찾는 것은 명시적인 새 관찰 경로이며 실패한 ref를 몰래 대체하는 수단이 아니다.

0.5~1초 입력 간격, 모호함 거부, 결과 불명 중복 실행 금지, 위험 확인, 요청 ID 기록을 유지한다. 계획 전체에 confirmed=true를 전파하지 않는다. 확인이 필요한 단계에서는 중단하고 해당 동작에 한정한 확인 범위를 요구한다. 검색어·링크 모양만으로 안전하다고 자동 승격하지 않는다.

외부 부작용이 있는 동작은 일반 검색 계획의 자동 진행 대상으로 확대하지 않는다. 최초 구현의 자동 진행은 조회·검색·필터 등 검증 가능한 UI 흐름에 집중한다. 필터가 서버에서 조회를 수행하는 사실과 예약·구매 같은 과업 부작용은 구분하되 도메인 특례로 해결하지 않는다.

### 3. 관련 전환을 확인하는 작은 계획 실행기

정해진 문자열 클릭 목록이나 전체 페이지 정지 대기가 아니다. 각 단계가 대상 조건·행동·다음에 확인할 사실·중단 조건을 가진다. 첫 버전은 분기·반복문 없는 짧은 순차 계획으로 제한한다. 새로운 의미 선택은 LLM에 돌려준다.

예시: `여행지 입력 → 지정 listbox 안의 종로구 후보가 유일하면 선택 → 지정 날짜의 현재 선택 가능 버튼 확인 → 선택 결과 확인`.

완료 조건은 값 일치, 그룹 선택값, 새 메뉴·문서·URL, 특정 영역의 결과 교체, 정해진 문구 존재처럼 관찰 가능한 술어만 지원한다. '가성비 좋음', '적합한 호텔', '구매 버튼이 아님'은 엔진 술어로 만들지 않는다.

특히 조작 직후 기존 후보가 하나라도 남았다는 이유로 다음 단계로 넘어가지 않는다. 관련 결과 영역의 갱신 근거를 확인한다. URL·busy·관련 DOM 교체와 기대 필드를 함께 사용하고, 보장할 수 없는 경우 bounded timeout 뒤 미확인으로 반환한다. 임의 시간의 무변화를 페이지 완성의 증거로 쓰지 않는다.

관찰은 원자적 화면 동결이 아니다. 수집 시작/끝의 문서와 관련 범위의 변경을 확인하고, 섞였을 가능성이 있으면 해당 근거로 다음 동작을 승인하지 않는다. 무관한 광고·시계 변화 때문에 전체 페이지를 무한 대기하지 않는다.

입력 시작값: 계획 최대 4개 행동, 총 20초 예산, 개별 후속 조건 관찰 최대 3초. 수치는 조정 가능한 초기값이다. 예산 초과는 실패한 행동의 재실행 근거가 아니다. 설정 자체에 상한을 둔다.

### 4. 작은 반환과 예외 복귀

일반 성공에서는 수행한 단계, 새 결과, 다음 목표에 필요한 후보·변화만 반환한다. 이전에 전달한 동일 정보는 명시적 소비자·응답 기준으로 접는다. 다른 에이전트나 전달하지 않은 내부 관찰을 LLM의 지식으로 간주하지 않는다.

정지 시 항상 보존:

- 끝난 단계, 시도했으나 결과 불명인 단계, 실행하지 않은 단계.
- 마지막 실제 실행 결과와 확인 상태. 명령 완료·전환 확인·사용자 과업 성공을 구분.
- 멈춘 이유와 현재 판단에 필요한 소수 후보·소속·일치 근거.
- 다음에 필요한 최소 조회 범위 또는 사용자/LLM 선택 항목.

요청 ID와 단계별 ID를 남겨 타임아웃 후 상태 조회가 가능하게 한다. 재호출을 전체 재실행으로 해석하지 않는다. 중단·취소 이후에도 이미 실행된 부작용을 취소했다고 기록하지 않는다.

## B플랜은 기본 계약의 일부

1. **0개:** 범위/부분 수집/새 영역/지연 여부를 먼저 분리. 근거가 있을 때 제한 관찰하고 필요한 범위 한 단계만 확대.
2. **복수:** 소속·목적지·상태가 붙은 소수 후보 반환. 동일 href나 첫 순서로 대체하지 않음.
3. **빈 이름/이름 불일치:** 보이는 원문과 실제 컨트롤 관계로 찾아 ref 실행. 이름을 지어내지 않음.
4. **재렌더/옛 후보:** 현재 영역을 다시 관찰해 새 대상을 선택. 옛 후보를 자동 연결하지 않음.
5. **새 팝업:** 열린 영역의 로컬 목표 조회. 확인 없이 닫거나 기본 작업을 다시 제출하지 않음.
6. **검증 불가/결과 불명:** 해당 단계에서 중단. 상태 조회·읽기로 적용 여부부터 확인.
7. **계속되는 맥락 부족:** 관련 패널/항목만 HWM 상세로 확대. 반복 감지는 확대를 제안하는 근거이지 자동 조작 권한이 아님.
8. **접근 차단:** 사실 보고. headless 고정/자동 headed 허용 같은 세션 실행 정책을 복구에도 동일 적용.

자동 복구는 읽기와 범위 조정 중심으로 한 번까지만 시작한다. 같은 실패가 반복되면 후보와 근거를 돌려준다. 대규모 재탐색·스크립트 생성으로 이어지지 않는다.

## 코드 배치와 기존 기능 처리

새 조정 계층은 `src/runtime/task/` 아래에 둔다. schema, observe, transition, run, result를 책임별 작은 모듈로 분리한다. 이는 전부 별도의 거대한 서브시스템이 아니라 하나의 과업 실행 루프를 구성한다.

- `runtime/task/schema.ts`: 목표·대상 조건·단계·검증·예산·정지 사유 계약.
- `runtime/task/observe.ts`: 공통 수집기를 통한 범위 선택·목표 후보·근거 조립. 새로운 독립 이름 계산기 금지.
- `runtime/task/transition.ts`: 관련 영역 전후 관찰과 제한 대기. DOM 변경과 업무 성공을 혼동하지 않음.
- `runtime/task/run.ts`: 순차 단계 실행·중단·요청 상태. executePrimitive를 직접 호출하며 RPC를 자기 자신에게 보내지 않음.
- `runtime/task/result.ts`: 공통 반환·전달 기준·마스킹 적용.

기존 `snapshot.ts`, `hwm/observation.ts`, `observation/service.ts`의 중복 수집·이름 계산은 얇은 공통 브라우저 수집 모듈로 단계적으로 추출한다. 기능을 잃지 않도록 역할·이름·그림자 DOM·텍스트·상태·관계의 fixture를 먼저 고정한다. 모든 상세 수집을 매번 실행하는 단일 거대 함수로 합치지 않는다.

`engine/execute.ts`, `references.ts`, `request-store.ts`의 검증된 계약을 사용한다. 필요한 경계를 바꾸더라도 가드와 실행 결과의 강도를 약화하지 않는다. 기존 `batch`는 이미 확정된 입력 묶음이며 새 계획은 단계 사이를 관찰한다. 둘의 계약을 억지로 합치지 않는다.

`browserd/server.ts`는 세션·직렬화·모드 정책을 유지하는 어댑터로 얇게 만든다. 새 실행기는 내부 함수 호출로 연결해 현재 직렬화 락 재진입 문제를 피한다. 기존 단일 명령도 같은 코어의 한 단계로 연결해 두 실행 경로가 갈라지지 않게 한다. 저장 액션도 공통 실행 가드를 유지하며 이번 변경 때문에 자동 학습되지 않는다.

CLI/RPC는 논리적으로 `찾기`, `조작+후속목표`, `짧은 계획 실행`, `요청 상태 확인`을 제공한다. 정확한 명령명은 구현 계약을 확정할 때 정한다. 옵션을 다 알아야만 조회할 수 있는 인터페이스는 피한다. 현재 at 핸들은 위치·전달 기준이며 권한이나 실행 대상 ref로 혼용하지 않는다.

민감값은 관찰 데이터 경계에서 마스킹해 일반 JSON·HWM·inspect·로그에 동일 적용한다. 목표와 계획의 임시 저장에는 TTL·용량 제한·세션 종료 정리를 적용한다. 실행에 필요한 실제 값과 공개 보고 값을 분리한다.

## 개발 순서와 각 완료 기준

### 1. 공유 대상 모델과 조회

기존 수집에서 공통 이름·텍스트·소속·ref 등록을 추출하고 목표 조회를 연결한다. 임시 goal-follow는 비교 자료로만 둔다.

완료 기준: 자동완성 중복 텍스트, 이름 없는 평점, 열린 shadow, 중복 링크, 대화상자 뒤 배경, 마스킹 사례에서 사실과 대상 연결이 정확하다. 반환한 ref를 직접 실행할 수 있으며 이름 재검색을 요구하지 않는다.

### 2. 조작과 후속 목표를 한 코어 호출로

한 행동을 실행한 뒤 관련 effect와 후속 목표를 같은 결과로 반환한다. 실패해도 원래 실행 결과를 유지하고 읽기 전용 근거를 함께 줄 수 있다.

완료 기준: 평소 흐름은 한 요청으로 진행하고, 실패·확인 필요·결과 불명이 성공으로 바뀌지 않는다. 새로운 영역 조회가 전체 페이지 출력으로 커지지 않는다.

### 3. 전환 확인과 짧은 조건부 계획

로딩 중 옛 목록, 필드 초기화, 문서 교체, 늦은 자동완성, 새 팝업을 관찰하며 유일 조건·명시 검증이 충족될 때만 다음 단계로 간다.

완료 기준: 정상 작은 계획은 중간 모델 호출 없이 수행한다. 0/복수/검증 미확인/시간초과/결과 불명에서 다음 행동이 실제로 실행되지 않는다. 부분 완료가 정확히 보고된다.

### 4. 기본 흐름 전환과 SKILL 정리

기본 스킬 흐름을 목표 중심으로 바꾸고 기존 단일 명령을 공통 코어로 연결한다. 반복되는 패널·관찰 옵션 설명을 줄인다. 상세 조회와 HWM은 필요할 때 사용한다.

완료 기준: 작은 목표·조건만으로 통상 흐름을 시작할 수 있다. 출력에 이미 있는 후보를 다시 묻지 않으며, 상세 출력 없이는 진행 불가능한 설계가 되지 않는다. 문서와 실제 실패 반환 계약이 일치한다.

### 5. 같은 과업의 전체 비용 검증과 중복 제거

기존 HB와 새 코어를 동일 과업·동등한 근거·동일 모델 조건에서 비교한다. 외부 사이트는 소수만, 학습은 끄고, 차단은 별도 분류한다. 로컬 fixture로 실패·안전 경계를 먼저 검증한다.

완료 기준: 성공률·잘못된 실행·불필요한 반복이 악화되지 않고, 왕복·전체 토큰·복구 포함 시간의 개선 여부를 확인한다. 고정 성능 개선율은 사전에 약속하지 않는다. 실측 후 기본 예산을 조정하고 쓰이지 않는 중복 경로를 제거한다.

## 반드시 다룰 검증 사례

- 같은 문구지만 다른 폼·다른 목적지, 같은 href의 여러 링크.
- aria-hidden 시각 텍스트와 빈 accessible-name, 날짜 선택 후 이름 변경.
- 포털 메뉴·열린 shadow·접근 불가능 프레임·부분 수집.
- 필터 직후 옛 목록, 늦게 바뀌는 URL·값, 광고만 계속 갱신되는 페이지.
- 단계 실행 뒤 응답 타임아웃·데몬 재시작·문서 교체·취소.
- 위험 확인이 중간에 발생하는 계획, 외부 쓰기 자동 진행 거부.
- 전달 기준이 다른 소비자, 만료 핸들, 최근 전달했으나 현재는 무효인 정보.
- headless 고정 정책과 자동 headed 허용 정책의 복구 경로 차이.

순서는 로컬 실제 브라우저 fixture → 공통 계약 회귀 → 소수 실전 과업이다. 계획 문자열을 잘 읽는 것만 검증하지 않는다. 외부 사이트별 예외 코드는 넣지 않는다.

## 이 설계에서 가장 중요한 선택

최적화 단위는 한 번의 클릭도 전체 사이트 러너도 아니다. **LLM의 새로운 판단 없이 확실하게 진행할 수 있는 가장 작은 과업 구간**이다. 그 구간의 관찰·실행·전환 확인을 HB가 맡고, 판단이 필요해지는 순간 충분히 작은 근거와 함께 LLM에 돌려주는 것이 코어다.
