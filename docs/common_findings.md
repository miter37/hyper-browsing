### 기록 범위와 상태

HWM 0.1 초안 이후 사용자와의 논의, 다른 에이전트가 제시한 의견, 저장된 HB 실험 기록을 검토하며 얻은 발견이다. HWM 0.2 설계를 위한 기록이며, 아래 제안이 모두 구현됐거나 효과가 검증됐다는 뜻은 아니다. 새 사이트 접속이나 새 비교 실험은 수행하지 않았다. 당시 실행 결함 중 일부는 이미 수정됐으므로 과거 실패를 현재 결함으로 단정하지 않는다.

심층 검토한 사이트는 Best Buy, Amazon, Booking.com, eBay, Weather.com, IMDb의 6곳이다. Best Buy는 반복 미완료였으며 나머지는 최종 성공한 시행에서도 중간 실패와 복구가 나타난 사례다. Expedia는 선별 과정에서 확인했지만 반복 실패가 주로 CAPTCHA여서 제외했다. 다른 사이트의 CAPTCHA·접근 거부 구간도 표현 문법의 개선 근거와 구분했다.

### 최상위 설계 원칙 — 사용자와 확인

1. 공통 엔진과 표현 문법에 특정 사이트를 위한 예외 조치를 누적하지 않는다. 사이트 기록은 일반적인 문제를 발견하고 검증하는 사례로 사용한다. 의도적으로 사이트별 절차를 보관하는 별도 자산의 존재와 공통 엔진의 사이트별 예외를 혼동하지 않는다.
2. 웹의 정보·맥락·위치·관계·상태·변화를 최대한 기계적이고 결정적인 알고리즘으로 수집·계산하여 정해진 문법으로 LLM에 전달한다. LLM이 풍부한 근거를 받고 의미와 다음 행동을 판단하게 하는 것이 목표다.
3. 결정적이라는 말은 모르는 내용을 확정한다는 뜻이 아니다. 같은 관찰 데이터와 옵션에는 같은 출력 규칙을 적용하고, 사실·계산·추정·미관찰을 구별한다. 같은 URL의 동적 페이지가 언제나 같은 출력을 낸다는 보장은 아니다.
4. 출력 축약은 정보의 소속·관계·출처를 흔적 없이 삭제하는 방식이어서는 안 된다. 무엇을 생략했고 어떤 범위까지 확인했는지 드러낸다.

### 0.1 설계에서 보완할 공통 사항

- **관찰 그래프와 LLM용 표현 분리:** 0.1의 JSON 레코드는 저장·교환·검증에 적합하지만, LLM이 매번 up 포인터를 따라가는 것은 부담이다. 동일한 관찰 그래프에서 들여쓰기 중심의 읽기 쉬운 표현을 결정적으로 생성한다. 두 모델을 독립적으로 관리하지 않는다.
- **정보 보존과 읽기 비용 함께 고려:** 토큰을 무조건 최소화하지도, 모든 세부 정보를 매번 쏟아내지도 않는다. overview/focus/full을 두되 focus에도 필요한 조상·레이블·폼·제목·연결 대상과 조작 방해 상황을 유지한다.
- **기계적 계산은 적극적으로 제공:** URL 차이, 위치 관계, 반복 구조, 제목 문맥 등을 앱이 계산한다. 업무 의미 판단과 기계적 계산을 혼동해 원문만 넘기는 방향은 피한다.
- **관계 근거 구별:** HTML/ARIA 명시 관계, 좌표로 측정한 관계, 규칙으로 선정한 문맥은 서로 다르다. ARIA는 페이지 작성자의 선언이며 실제 동작 보장이 아니다. 기하학적 근접은 의미적 연관성을 보장하지 않는다.
- **들여쓰기 의미 명확화:** 장식용 래퍼를 축약한 유지 조상 관계다. 한 단계가 원본 DOM의 직접 부모 한 단계라는 뜻은 아니다. 폼 소유·ARIA 연결·Shadow DOM/slot 관계를 필요에 따라 별도로 유지한다.
- **좌표와 위치 관계 병행:** 내부에는 좌표계·사각형·스크롤·클리핑 정보를 보존하고 LLM에는 계산한 위/아래/근접 관계를 우선 제공한다. 같은 영역 안에서 부모가 다른 요소도 근접 후보가 될 수 있다. 모든 노드 쌍을 출력하지는 않는다.
- **관찰보다 강한 주장 금지:** target=_blank는 실제 새 탭 생성과 다르다. aria-modal=true는 전체 배경 가림을 증명하지 않는다. 중앙 한 점의 hit test를 전체 요소 가림으로 확대하지 않는다. 같은 경로의 쿼리 변경을 안전한 필터로 분류하지 않는다.
- **반복 구조와 반복 내용 구분:** 공통 구조 설명은 공유하되 항목별 제목·값·상태 차이는 우선 보존한다. 첫 항목 하나만 남기면 같은 구조 안의 중요한 차이가 사라질 수 있다. 내용까지 접으면 그 사실과 범위를 명시한다.
- **생략·미관찰·접근 불가·마스킹 구분:** 수집했지만 표시하지 않은 내용은 folded, 수집하지 않은 것은 unobserved, 읽지 못한 것은 unavailable, 숨긴 값은 redacted처럼 구분한다. 새 DOM 접근이 필요하면 새 관찰이다.
- **참조 수명 분리:** 관찰용 노드 ID와 실행용 actionRef를 구분한다. 같은 이름이나 같은 URL이 대상 동일성을 보장하지 않는다. 기존 실행 참조 계층과 연결하고 별도 참조 시스템을 중복 구축하지 않는다.
- **문법의 문자열 경계:** 페이지에 적힌 표식·지시문은 이스케이프된 콘텐츠로 취급한다. ASCII 기호만 사용해도 셸 인용 문제가 자동 해결되는 것은 아니다. 출력 문법과 명령 인자 전달을 각각 검증한다.

#### Booking.com — 문구 일치와 입력 후보 관계는 다르다

- 목적지 입력 직후 값 확인은 빈 문자열이었다. 이어 New York을 조회한 결과에는 추천 도시 카드·일반 도시 링크·날짜가 포함된 도시 링크가 섞였다. 후속 관찰의 입력란은 expanded=false였다. 같은 도시명이 보였다는 이유만으로 자동완성 후보라고 확정할 수 없다. 요약 기록의 자동완성 표현도 원시 출력보다 강하게 해석하지 않는다.

### 0.2 문법과 구현의 우선순위 제안

1. 소속·제목·일치 근거가 붙은 검색/후보 출력. query, scope, match 필드를 포함한다.
2. 입력란·연결 목록·대화상자와 조작 전후 변화. 실행 결과와 관찰 결과를 구분하며 outcome_unknown을 성공으로 바꾸지 않는다.
3. 읽은 값의 문서·관찰·영역 출처 및 단위·시간 문맥 보존.
4. 이를 유지하는 focus, 후보 차이 보존, 반복 구조의 접힘/펼침.
5. 추가 공간 관계와 정확한 좌표 상세 조회.

새 기호를 계속 늘리기보다 기존 노드·관계·출처·변화에 필요한 필드를 명확히 정의한다. 위 필드명은 설계 제안이며 구현된 API 계약이 아니다. 어떤 내용들을 합쳐 표시하더라도 원래의 조각과 관계를 잃지 않는다.

### 설계상 깨달은 점

- **정본과 LLM 뷰를 나눈다.** 위 기록과 같은 결론이다. 덧붙이면, 포인터(`up`)로 표현한 트리는 노드가 수백 개일 때 "이 값은 어느 항목 소속인가"를 LLM이 체인을 따라가며 풀어야 한다. 들여쓰기는 같은 정보를 *보이게* 한다.
- **근거는 기호로, 경고는 최소로.** 관찰 사실(무기호), 명시 연결(`->`), 측정(`~`), 규칙 추정(`^`)을 기호로 구분하면, 범례에 "단정하지 마라"를 반복할 필요가 없다. 경고가 쌓이면 LLM이 재관찰을 반복하며 판단을 미룬다. 그래서 검증 지표에 추가 관찰 호출 수와 시간을 함께 둔다.
- **앱은 이름 붙이지 않는다.** 제가 0.2 검토에서 쓴 `template: … rating price fulfillment`, `badge=`, `price basis`는 앱이 의미를 붙인 것이라 원칙 2에 어긋났다. 템플릿은 구조 모양(`text link text button`)만, 텍스트는 원문 순서대로 쓴다.
- **휴리스틱은 표준 근거로 바꾼다.** "콜론으로 끝나면 hint", "폼 근처 짧은 안내", "스켈레톤 감지"처럼 사례에서 만든 조건은 사례가 늘면 누더기가 된다. `role=status`/`aria-live`, `aria-busy`, `label for`, DOM 포함처럼 표준에 정의된 근거만 쓰고, 나머지는 측정값으로 전달한다.
- **"최대한 많이"와 "묻히지 않게"의 긴장은 접기로 푼다.** 앱이 중요도를 판단해 버리지 않는다. 반복 구조 접기, 같은 href 색인, 화면용·스크린리더용 중복 제거처럼 사이트 무관한 기계적 규칙으로 접고, 흔적을 남기고, 펼칠 수 있게 한다.
- **위험도 엔진도 같은 그래프를 쓰는 편이 낫다.** 같은 문서에서 쿼리만 바뀌는 링크인지, `href="#"`인지 같은 사실을 공유하면 단어 일치 기반 오탐을 구조적으로 줄일 수 있다. 다만 같은 경로의 쿼리 변경을 "안전"으로 분류하지는 않는다(위 기록의 주의와 같음).

### 0.2 우선순위 (위 기록의 제안과 합친 의견)

1. 항목 내용 텍스트와 문서 개요, 트리 경로로 돌려주는 검색 결과. 위 기록의 1번(일치 근거·scope가 붙은 검색/후보 출력)과 함께 구현한다.
