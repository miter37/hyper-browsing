# Booking 순차 요청 보완 후 재수행

2026-10-16 09:25 KST · GPT-6 Codex

조건: 2027-01-05 인천→파리, 2027-01-11 파리 출발 귀국, 성인2명/이코노미. Booking 항공권 첫 화면부터 다시 시작했다. 기존 headed dy1 탭 하나와 프로젝트 스킬/CLI, 임시 sequence-spike 실행기를 사용했다. 예약·결제·학습 없음.

## 수행 전에 반영한 보완

- 기본 출발지 칩 제거처럼 DOM이 바뀌는 조작 뒤에는 과거 ref 대신 관찰한 역할/이름으로 다음 대상을 다시 찾았다.
- 현재 한국어 UI에 맞춰 파리를 입력했고, 선택 결과에 PAR 코드까지 표시될 것이라는 검증 문구 추측을 제거했다.
- 최종 관찰에 waitMs/minMatches를 지원했다. 카드 추출에는 비어 있지 않은 값과 지정 문자열 조건을 지원했다. URL 변경만으로 카드 준비를 대신하지 않았다.
- 카드 경계를 이미 관찰했으므로 list/item의 추정을 반복하지 않고 기존 extract로 카드3개를 읽었다. 조건은 현재 과업의 입력값이고 공통 코드에 도메인 분기를 추가하지 않았다.

## 실제 과정

1. 서울 모든공항 초기값 제거→ICN 입력, ICN 선택→도착지 열기→파리 입력, 파리 선택→달력 열기→다음달 이동을 각각 최대4단계 요청으로 수행했다. 앞선 stale_ref/영문 지명/요약 검증 오류는 재발하지 않았다.
2. 실제 달력에서 2027년1월5일·11일을 확인했다. 날짜2개 선택→탑승객 열기도 연결했다.
3. 인원 관찰이 실패했다. 모델이 성인/완료/확인/늘리기 같은 이름을 예상했지만 실제 완료 버튼 이름은 선택이었다. 성인 증가 버튼은 화면에 보이나 aria-hidden=true, tabindex=-1인 버튼이고, 주 입력은 input type=range role=spinbutton이었다. 기본 목표 수집은 이 시각적 조작들을 반환하지 못했다.
4. 이미 열린 팝업을 다시 클릭하지 않았다. 읽기 확대가 유효 정보를 주지 않아 스크린샷과 해당 위치의 제한된 DOM 읽기로 확인했다. 관찰한 성인 plus 버튼을 공통 click의 CSS 경로로 한 번 눌렀다. 기존 extract로 range 값2를 확인한 뒤 선택을 눌렀고, 외부 탑승객 성인2명 요약도 검증했다. 이 선택자는 제품에 등록하지 않았다.
5. 선택 적용→검색→날짜가 포함된 카드 읽기를 한 요청으로 실행했다. 실제 카드가 나타날 때까지16.070초 기다려 결과를 반환했다. 빈 조회를 성공으로 넘기지 않았다. 다만 CLI 추출을23회 조회해 비용이 컸다.
6. 그 경험으로 임시 실행기의 후속 추출에 기존 wait-for --css를 먼저 호출하도록 바꿨다. 그 뒤에도 내용 조건을 확인한다. 이후 최저가순은 첫 카드의 최저가 표시, 직항 조회는 반환 카드들의 직항/날짜 문자열을 확인했다. 직항 변경+관찰은3.795초/내부3호출/카드내용확인1회였다. 첫 검색과 다른 캐시·전환 조건이므로 대기 개선율로 비교하지 않는다.
7. 직항 최저가와 대한항공 Standard의 상세 창을 각각 열기+본문 조회로 읽어 운항사·총액·수하물을 확인했다. 상세의 '총 요금(탑승객 전원)' 표시를 확인해 1인 가격과 혼동하지 않았다.
