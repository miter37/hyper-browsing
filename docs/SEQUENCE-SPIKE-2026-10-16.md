# 최대 4단계 조작·관찰 연결: 임시 실전 실험

2026-10-16 09:03 KST · GPT-6 Codex

## 범위와 질문

사용자 요청에 따라 정식 아키텍처를 확정하지 않고 임시 실행기와 프롬프트를 만들었다. 질문은 '현재 근거로 예상 가능한 조작을 묶고 마지막 관찰까지 요청하면 모델의 중간 재판단을 줄일 수 있는가, 어디에서 멈춰야 하는가'였다.

프로젝트 스킬과 CLI만 사용했다. 기존 dy1 headed Chrome의 탭 하나를 재사용했고 추가 창·학습·영구 사이트 자산·API 우회는 없었다. 루트가 직접 수행했다. 프로토타입은 `.runtime/sequence-spike/run.mjs`, 프롬프트는 같은 폴더의 `PROMPT.md`, 요청 JSON과 실행별 원본 로그도 그 폴더에 있다. 런타임 폴더는 Git 대상이 아니며 제품 기능으로 등록하지 않았다.

## 임시 실행 방식

한 요청은 조작 0~3개 뒤에 관찰 1개, 총 최대4단계다. 관찰만 필요한 회차도 허용한다. 조작은 기존 task.run에 넘겨 참조·모호함·승인·0.5~1초 입력 간격·조건부 검증을 재사용했다. 마지막 관찰은 find, map, 지정 제목 범위 read 중 하나다. 조작과 관찰 모두 고유 단계ID와 상태를 기록한다. 모든 요청을 미리 검증하고, 후속 조작을 시작하기 전에 앞 조건을 확인한다.

모델은 요청 하나를 작성한 뒤 최종 응답까지 끼어들지 않았다. 내부 CLI가 한 개라는 뜻은 아니다. 예를 들어 제목 범위를 읽으려면 내부적으로 map→outline→해당 section read가 필요했다. 이 내부 호출 수와 내부 stdout, 모델이 받은 최종 응답량을 구별해 기록했다.

중단 시 전체 요청을 처음부터 재실행하지 않는다. v1은 조작 검증 실패 시 마지막 관찰도 중단했다. HN의 실제 막힘을 보고 v2에서는 이미 조작이 완료됐고 outcome_unknown이 아니라면 마지막 읽기만 recovery로 수행했다. 전체 요청의 미확인 상태는 유지한다. 읽기로 성공을 대신 선언하지 않는다.

## 주요 실전 결과

아래 시간은 요청 제출부터 관찰 응답까지다. 최초 접속·이전 상황 확인·계획 작성·프로토타입 개발 시간은 제외한다. 서로 다른 과업이므로 기존 방식 대비 개선율은 산출하지 않았다.

| 사이트 | 한 요청에 넣은 단계 | 요청 시간 | 내부 CLI | 내부 stdout | 모델 최종 응답 |
|---|---|---:|---:|---:|---:|
| MDN | 검색창 열기→Array.prototype.filter 입력→전체 검색 선택→검색 결과 두 제목 범위 읽기 | 7.020초 | 5 | 13,604B | 8,104B |
| Wikipedia | 글자 Large→폭 Wide→테마 Dark→현재 선택3개 확인 | 4.809초 | 2 | 3,133B | 3,332B |
| Hacker News | 이름 없는 검색 입력에 SQLite→Enter 제출→결과 조회 | 5.247초 | 2 | 8,208B | 4,930B |

세 주요 과업은 실행과 요청한 관찰이 완료됐다. MDN 결과 첫 항목은 지정 출력 한도로 일부만 전달됐으며 complete=false/nextRead가 있었다. 관찰 완료를 본문 전체 수집이나 과업 의미 검증으로 확대하지 않는다. HN은 실제로 Algolia 검색 화면으로 이동했다. 입력값과 URL, 반환된 결과의 제목/목적지를 확인했다.

Wikipedia는 원래 Appearance가 열려 있었다. 이를 확인하고 세 설정을 변경한 것이며 가상의 팝업을 열었다고 기록하지 않는다. 종료 전 Standard 글자/Standard 폭/Light로 원복했고 체크 상태3개를 확인했다(원복3.641초, 기본 결과 표에서 제외).

## 시행착오와 수정

### 1. 결과를 문서 전체에서 읽으면 조작 연결이 빨라도 쓸모가 없다

앞선 MDN 시연에서는 document를 main처럼 읽어 메뉴가 먼저 나왔다. 이번에는 마지막 관찰 요청에 'level2 제목의 첫2개 범위'를 넣고, 실행기가 현재 페이지의 실제 outline에서 그 범위를 선택했다. 특정 사이트 선택자는 넣지 않았다. 결과 제목 Array.prototype.filter()/TypedArray.prototype.filter()와 링크를 받았다.

다만 제목 순서는 모든 사이트의 결과 목록을 대체하지 않는다. 실행기 안에 사이트별 결과 탐색을 숨길 것이 아니라, 모델이 관찰 목적과 범위를 명시하고 찾지 못하면 작은 지도를 반환하는 방향이 맞다.

### 2. 모든 단계를 채우는 것보다 판단 경계를 잘 자르는 것이 중요하다

HN의 기간 필터는 처음에 내용을 몰랐으므로 '열기→선택지 읽기' 두 단계로 요청했다. All time/Last24h/Past Week/Past Month/Past Year/Custom range를 실제로 받은 뒤 선택을 진행했다. 처음부터 Custom range의 조작 절차를 추측하지 않았다.

### 3. 새 화면을 확인할 수 있는데 오래된 컨트롤 검증까지 요구하면 느려진다

첫 HN 열기 요청은 fields.expanded=true와 새 listbox 등장 두 조건을 요구했다. 실제 메뉴는 열렸지만 클릭한 ref가 stale이 되어 3초 확인 후 target_replaced로 멈췄다(4.274초). 클릭을 재실행하지 않고 선택지만 읽어 복구했다(0.431초).

프롬프트를 바꿔 '새 listbox 등장'이라는 충분한 조건만 사용한 두 번째 열기+관찰은 1.858초, 내부2호출, 최종2,918B였다. 이는 통제된 성능 비교가 아니라 실패 원인을 줄여 재시도한 사례다. 컨트롤은 다른 기간 이름으로 바뀌어 있었고 실행 시점도 다르다.

### 4. 조작 정지와 읽기 정지를 분리해야 한다

v2 경계 시험에서는 All time 옵션을 선택한 뒤, 사라질 수 있는 옵션 자체의 selected를 검증하도록 의도적으로 요청했다. target_replaced로 검증은 미확인이었지만, 마지막 안전 조회는 recovery로 실행했다. 현재 바깥 combobox의 All time과 실제 dateRange=all URL을 반환했다. 전체 ok=false, 조작 completed, 관찰 completed/purpose=recovery를 동시에 유지했다(4.622초). 검증에 실패했다고 클릭을 반복하지 않았다.

이는 정상 운영에서 그 검증을 권장한다는 뜻이 아니다. 실제 실패에서 발견한 조건을 재사용해 recovery 경로를 시험한 것이다. 정상 프롬프트는 선택 후 지속하는 바깥 값을 확인하도록 바꿨다. Past Year 선택+결과 조회는 그 방식으로 1.613초에 완료됐다. 필터 표시 변경만으로 목록 갱신 전체를 보증하지는 않는다.

### 5. 모호한 대상은 묶음 실행에서도 그대로 멈춰야 한다

Wikipedia의 Standard radio는 글자와 폭에 각각 하나씩 있었다. 경계 시험에서 이름만 지정하자 두 후보를 반환하고 실제 클릭 전에 target_ambiguous로 정지했다(0.490초). 원복은 이미 관찰한 서로 다른 ref로 실행했다. 묶음 실행이 임의의 첫 후보 선택을 정당화하지 않는다.

### 6. 문장 강조도 코드 강조와 같은 출력 문제를 만든다

MDN 검색 결과는 강조용 span 때문에 문장이 작은 text 항목으로 나뉘었다. 임시 출력 투영에서 같은 문단/제목 아래의 텍스트를 순서대로 연결하고 링크 참조·목적지·소속과 부분 표시를 유지했다. 동일한 MDN 관찰 자료의 observation 부분은 6,025B→2,640B였다. 브라우저 재수행이나 속도 비교가 아니라 보유한 동일 원문에 대한 표현 실험이다. 개별 텍스트 조각의 ID는 원본 로그에 남기고 최종 뷰에서는 접었다. 정본과 완전히 같은 정보를 무손실로 출력했다고 주장하지 않는다.

## 이번에 사용하고 다듬은 프롬프트

> 현재 근거로 다음 판단 지점까지 조작과 관찰을 합쳐1~4단계로 요청한다. 기본은 조작1개+관찰1개다. 충분히 예상 가능하면 조작2~3개 뒤 관찰을 붙이고, 단계 수를 채우지 않는다.
>
> 대상은 관찰한 ref 또는 유일하게 찾을 수 있는 이름·역할·소속으로 지정한다. 모르는 다음 화면은 열기+그 안 관찰로 끝낸다. 각 단계에는 다음 진행에 필요한 최소 조건만 붙인다. 사라질 옵션 자체보다 지속하는 선택 요약을 확인한다.
>
> 마지막에는 어느 범위에서 무엇을 얼마나 받아 판단할지 명시한다. 결과 본문을 문서 전체로 대신하지 않는다. 메뉴 선택지·폼 현재값·항목 내용 등 필요한 정보만 받는다. 부분 수집과 잘림은 그대로 읽는다.
>
> 조작이 중단되면 완료한 단계를 반복하지 않는다. 뒤의 조작은 정지하되, 실행 여부가 알려져 있고 안전하게 읽을 수 있으면 현재 상태를 recovery로 반환한다. 전체 성공으로 바꾸지 않는다. 실행 여부 불명은 요청 상태 확인으로 넘긴다.

## 현재 권고: 유지할 기반과 아직 확정하지 않을 부분

유지할 기반은 '조작과 관찰을 같은 단계 목록에 넣기', '다음 판단 경계까지 묶기', '단계별 상태와 요청ID', '기존 공통 실행 계층 재사용', '완료한 쓰기를 반복하지 않는 중단/읽기 복구'다. 세 사이트에서 실제 가능성을 확인했다.

관찰 대상을 찾는 정식 계약과 최소 출력 투영은 더 다듬어야 한다. 특히 자동 map/outline/read 비용과 결과 목록 갱신 확인은 남아 있다. 이번 프로토타입을 그대로 제품 코어에 복사하거나 모든 단계에 복잡한 검증을 강제하는 것은 권하지 않는다. 작은 묶음으로 판단 대기 구간을 줄이는 효과와 과도한 검증이 만든 지연을 함께 측정해야 한다.

정식 스킬/제품 코어에 새 시퀀스 기능을 이식하지 않았다. 본문에 인용한 시간은 전체 에이전트 작업 시간이나 기존 대비 개선율이 아니다. 이전 시연에서 발견해 수정한 native CLI run 옵션 분기1줄은 별도의 미커밋 변경으로 남아 있으며, 본 임시 실행기와 구별한다.
