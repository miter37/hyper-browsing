# 웹 UI를 필요한 범위만 읽으며 사용하는 법

이 문서는 LLM의 탐색 지식이다. 엔진이 특정 사이트의 메뉴 의미나 다음 행동을 자동 결정하는 규칙이 아니다. 아래 패턴은 가설을 세우는 데 사용하고 현재 응답의 DOM/ARIA 상태·역할·이름·소속으로 확인한다.

## 추가 메뉴와 팝오버

점 세 개, 더보기, 펼침 화살표는 추가 선택지를 여는 경우가 많다. 클릭 응답에 `focus.items`와 실행 ref가 있으면 그 정보로 선택한다. 메뉴 전체를 다시 묻거나 페이지 지도를 새로 받을 필요가 없다. 실제 역할이 menuitem인 요소를 이름만 보고 link로 호출하지 않는다.

큰 팝업의 `focus`가 일부 컨트롤만 제공하면 `focus.at`으로 필요한 `controls` 또는 `content,controls`를 요청한다. 여러 focus가 있으면 역할·이름·소속으로 현재 과업에 맞는 범위를 고른다. 단순히 첫 번째라는 이유로 선택하지 않는다. 열린 영역을 찾지 못했으면 이전 정보를 현재 메뉴라고 취급하지 않고 필요한 범위만 관찰한다.

## 페이지 이동, 탭과 사이드바

문서가 바뀌면 새 지도에서 제목·주요 패널을 확인한다. 명확한 다음 컨트롤이 이미 있으면 행동한다. 내용이 길고 필요한 설정이나 절을 아직 못 찾았다면 본문 패널의 `outline`을 읽고 그 구역의 `at`을 사용한다. 전체 설정을 offset으로 순차 열람하는 것을 기본 탐색법으로 삼지 않는다.

`current`는 실제 aria-current 값, `selected`는 관찰된 선택 상태다. 없으면 현재 항목을 확인하지 못했을 수 있다. URL·제목은 별도의 근거다. 탭이나 사이드바를 눌렀어도 문서가 그대로일 수 있으므로 새 페이지라는 추측으로 기존 정보를 모두 재요청하지 않는다.

## 폼, 자동완성과 적용

텍스트 입력, 추천 선택, 제출을 구분한다. combobox에 입력한 직후 listbox가 열리면 그 안의 실제 후보를 읽어 선택한다. 같은 문구가 본문 카드에도 있을 수 있으므로 이름 일치만으로 자동완성 후보라고 판단하지 않는다.

입력창의 값은 편집 중 값일 수 있다. 검색이나 필터를 적용한 뒤에는 현재 과업에 필요한 URL 조건·폼 값·선택 상태·결과 안내를 비교한다. 변경되지 않았다는 관찰도 정상 정보다. 명령 완료는 적용 성공을 뜻하지 않는다.

## 대화상자와 방해 요소

대화상자는 날짜·인원·메뉴·승인 등 현재 작업의 일부일 수 있다. 먼저 로컬 내용을 읽는다. 가로막힘이 보고되면 obstruction의 검사 지점과 가린 요소를 확인한다. 작업 UI 자체를 방해 요소로 분류해 닫지 않는다.

같은 대화상자 안에서 조작한 응답은 로컬 변화부터 읽는다. 다음 버튼을 찾기 위해 전체 snapshot을 반복하지 않는다. `observationError`가 있더라도 이미 실행된 동작을 되풀이하지 말고 필요한 상태만 조회한다.

## 항목과 표

상품명·가격·배송 조건·버튼은 같은 항목의 원문과 소속으로 짝짓는다. 숫자 하나의 의미를 이름이나 위치만으로 확정하지 않는다. 표에서는 행과 헤더 근거를 확인한다. `--item`은 DOM 순서이며 광고·숨은 항목을 의미적으로 제외한 순서가 아니다.

## 추가 조회를 고르는 기준

| 부족한 근거 | 요청 |
|---|---|
| 어느 구역에 있는가 | 해당 패널의 outline |
| 어떤 선택지가 있는가 | 해당 focus의 controls |
| 값과 설명·버튼이 어떻게 묶이는가 | 해당 항목의 content,controls |
| 입력·선택이 적용됐는가 | 관련 state와 결과 문구 |
| 위 정보로도 관계·위치가 모호한가 | 해당 범위의 explain |

받은 최신 `at`으로 이어가며 아직 필요한 근거만 요청한다. 페이지에 알 수 없는 정보가 있다는 이유만으로 전수 조회하지 않는다. 같은 조회가 진전을 만들지 않으면 want·scope·match·coverage를 먼저 검토하고 범위를 바꾼다.
