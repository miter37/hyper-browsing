# 달력·가격 필터 실전 조사와 공통 대응 전략

작성: 2026-10-16 · GPT-6 Codex, 직접 수행

## 조사 범위

현재 프로젝트의 SKILL과 launcher/webctl로 **헤디드 Chrome에서 13개 사이트를 방문했다. 달력 또는 가격 필터를 실제 열어 조작한 10개 사이트를 주 조사에 포함**했다. Amazon의 가격 정렬은 보조 사례이며 가격 범위 필터 발견으로 세지 않았다. Walmart는 CAPTCHA 이후 중단했고, Newegg는 국가/쿠키 안내와 불완전 탐색 뒤 가격 필터를 확인하지 못해 제외했다. 로그인·구매·예약·결제·CAPTCHA 우회·학습 자산 생성은 하지 않았다.

이는 정해진 과업의 속도 벤치마크가 아니라 조작 원리를 알아보는 탐색 조사다. 날짜는 주로 2026-11-10~12를 사용했다. Booking에는 추가로 900×900 화면 변형과 2027-01-10의 화면 밖 셀 선택을 시험했다. 동일 사이트의 화면 변형은 별도 사이트로 세지 않았다. 여행 사이트에서 날짜를 골랐다는 것은 검색 폼 설정의 확인이며 예약이나 숙소/항공권 검색 전체의 완료를 뜻하지 않는다.

원시 근거는 `.runtime/filter-study-2026-10-16/study/command-NNN.json`, 사이트별 JSON과 screenshots에 있다. [공유 색인](../benchmarks/filter-study-2026-10-16/evidence-index.json), [기록 하네스](../benchmarks/filter-study-2026-10-16/control.mjs), [탐색 도구](../benchmarks/filter-study-2026-10-16/explore.mjs)를 남겼다. eval은 DOM/CSSOM/입력 속성을 읽는 진단에만 썼고, 값·속성·이벤트를 주입해서 조작을 대신하지 않았다. 실제 조작은 HB click/fill/press/select/scroll로 했다. 연구용 사이트 URL·관찰 후 선택자는 조사 대상 지정이며 제품 규칙이 아니다.

## 이번에 분명해진 점

### 1. 같은 목표도 현재 조작 방식부터 찾아야 한다

“날짜를 고른다”를 무조건 Next 버튼 반복으로 바꾸면 틀린다. Booking은 1440px 화면에서는 두 달과 월 이동 버튼이 있었지만 900px에서는 여러 달을 담은 내부 스크롤이었다. 좁은 화면에 있던 Next는 Flexible date options의 가로 이동이었다. 사이트 이름만으로 알고리즘을 정하면 같은 사이트에서도 깨진다.

좁은 화면에서 실제 스크롤 DOM을 관찰해 만든 검증된 selector로 HB scroll을 호출했다. **element.scrollTop 296→516, 문서 위치는 그대로**였다. 다음으로 `Sunday, January 10, 2027`을 찾으니 `clipped=scroll`인 연결된 셀이 나왔다. 해당 ref 클릭은 기존 실행기의 scrollIntoView를 통해 내부 위치를 867로 옮기고 실제 1월 10일을 선택했다. 화면 밖이라고 반드시 월 이동/수동 스크롤이 먼저 필요한 것은 아니다.

대응 순서는 연결된 정확한 대상이 이미 있으면 현재 실행기의 스크롤 후 조작을 사용하고, 아직 DOM에 없는 대상이면 현재 작업면의 월 이동 또는 실제 내부 스크롤을 쓴다는 것이다. 비슷한 Next를 대신 누르거나 문서 전체를 내려서는 안 된다. selector는 이 조사에서 현재 DOM과 일치함을 검사한 임시 경로이며 영구 자산으로 저장하지 않는다.

### 2. 값이 들어감·위젯이 받아들임·검색에 적용됨은 다르다

실측된 세 사례가 서로 다르다.

- Best Buy: 두 fill의 valueMatches=true 뒤에도 URL은 그대로였다. Set 후에 가격 조건과 칩이 생겼다.
- Google Flights: Return의 fill은 성공했지만 정규화/selected 상태는 Tab 이후 나타났다. Done의 접근 가능한 이름도 그 뒤 바뀌었다.
- Hilton: 임시 13일이 버튼 이름에 나타났지만 Cancel로 기존 10~12일이 돌아왔다.

따라서 매 동작 뒤 추가 verify를 붙일 필요는 없지만, **입력 묶음의 끝에서는 위젯 밖 요약/활성 필터/결과 조건 중 필요한 근거를 한 번 읽어야 한다.** “아무 오류 없음”, “날짜 선택 색상 있음”, “dialog 닫힘”만으로 검색 적용을 주장하지 않는다. 반대로 정규화로 원문이 달라졌다고 무조건 실패로 처리하지 않는다.

### 3. 이름 문자열을 맞히는 비용이 크다

Booking은 `Tuesday, November 10, 2026`, Airbnb는 `10, Tuesday, November 2026…`, 한국어 사이트는 `2026년 11월 10일…`, Expedia/Agoda는 `10`이었다. 뜻은 같아도 단순 substring으로 찾으면 실패한다. 두 달의 동일 숫자에는 월·연도 소속이 필요하고, 날짜와 같은 좌표에 요금이 있는 경우 그 숫자를 날짜로 오인해서도 안 된다.

앱이 날짜를 임의로 해석하거나 번역해서 정답을 만들 필요는 없다. 먼저 실제 이름 표본, 월/연도 제목과의 구조적 연결, role·disabled·selected·DOM의 날짜 속성 등 근거를 좁게 주면 된다. 명시 속성/명시 연결, DOM 소속, 시각적 월 열의 연결은 근거를 구분해야 한다. 원본에 없는 ISO 날짜를 기계적 확정 사실처럼 추가하지 않는다.

범용 텍스트 검색에도 후보 하나 안에서 여러 단어를 모두 요구하는 검색과 구조 scope가 유용해 보인다. 이는 구현·효과 검증 전 제안이다. locale이나 사이트별 날짜 문자열 정규식을 늘리는 방식은 제안하지 않는다.

### 4. 가격 손잡이의 숫자가 표시 가격의 뜻 전부는 아니다

Booking의 현재 native range:

```text
Min.: value=30000 min=30000 max=590000 step=10000
Max.: value=600000 min=40000 max=600000 step=10000
```

Min.에 ArrowRight 한 번으로 value=40000, URL 하한 KRW-40000, 결과의 가격 칩을 확인했다. 그 뒤 Max.의 min도 50000으로 바뀌었다. 두 손잡이는 독립된 상수가 아니라 현재 값에 따라 제약이 달라진다.

또한 화면은 **KRW 40,000 – KRW 600,000+**였다. native max=600000을 “60만 원 이하”로 해석하면 틀린다. URL도 upper bound가 `max`인 상태였다. 최소/최대 숫자와 함께 통화, per night 같은 단위, `+`/이상/미만 같은 원문을 보존해야 한다. 사용 가능한 범위를 모르면 임의 환산하거나 근사 목표를 달성했다고 보고하지 않는다.

### 5. 조작 가능성은 보이는 사각형 크기와 다르다

Booking의 Min./Max. native range는 1×1px였고 target-center-covered였지만 키보드가 정상 동작했다. IKEA는 보이지 않는 input 대신 연결된 보이는 label로 선택했다. 이를 전부 “가려졌으니 실패”로 처리하면 유효한 표준 경로를 버린다.

선택 순서는 현재 DOM이 지원하는 방식에 따른다: 편집 가능한 숫자/텍스트 입력 → native select/checkbox/range의 표준 입력·키보드/연결 label → 필요한 경우 시각적 조작. readonly 날짜 input에 억지 fill, range에 일반 text fill, pointer-covered 입력에 무조건 force를 쓰는 방식은 피한다. 직접 입력이 가능하다고 해서 원시 값만 바꾸거나 이벤트를 합성하는 것은 이번에 시험한 경로가 아니다.

## 앱과 스킬을 어떻게 보완하는 것이 좋은가

### 우선 1: 작업면과 실제 조작 대상의 계약을 맞춘다

- panel/at으로 읽을 범위를 알았다면 그 패널의 실제 scroll owner도 안전하게 가리킬 수 있어야 한다. 현재 panel은 scroll 타깃으로 연결되지 않는다. 문서 스크롤로 조용히 대체하지 않도록 해야 한다.
- widget root 하나만으로 충분하지 않을 때는 내용 영역과 그것을 제어하는 명시적 컨트롤을 함께 조회할 수 있어야 한다. 두 달을 서로 다른 열로 쪼갰다면 공통 월 이동 컨트롤과의 연결을 잃지 않는다.
- active scope는 단지 role=dialog/menu가 있다는 이유로 정하지 않는다. Kayak/Trip에서 실제 작업 중인 달력 대신 상시 메뉴/다른 안내가 focus를 차지했다. 새로 열린 범위·실제 노출·실행 대상과의 관계라는 공통 증거를 우선해야 한다.

### 우선 2: 좁힌 요청에만 작은 조작 사실 묶음을 준다

새 기본 거대 스냅샷이나 달력 전용 덤프를 만들지 않는다. 대상 위젯을 열거나 해당 범위를 읽을 때만, 관찰 가능한 다음 사실을 기존 응답/그래프에서 함께 제공하는 방향이다.

```text
현재 root/ref 및 trigger/explicit controls 관계
현재 입력값·선택·disabled·readonly·invalid 상태
native type, min/max/step, aria-valuetext 등 실제 제약
보존된 제목/label/legend/caption 및 연결 근거
현재 노출 범위/실제 scroll owner/표본 개수와 미관찰 범위
관찰한 닫기·적용·취소 컨트롤 후보(원문 이름, 의미 단정 없음)
```

역할·원문·관계·제약을 주고 사용법과 의미는 LLM이 판단한다. 예를 들어 버튼 이름 Set을 그대로 전달하며 “이 사이트는 Set을 누르면 확정”이라는 사이트 규칙을 공통 코드에 넣지 않는다. 이 묶음도 매번 모두 주는 것이 아니라 현재 요청과 변경된 필드에 한정한다. 특히 60~300개 날짜 셀 대신 목표 날짜/현재 값/월 이동 컨트롤부터 조회할 수 있어야 한다.

### 우선 3: 계획은 2~4개로 묶되 변하는 ref는 그 단계에서 찾는다

- 모르는 위젯: 열기 + 현재 위젯/목표 후보 읽기.
- 읽은 숫자 필터: 하한 입력 + 상한 입력 + 관찰한 적용 컨트롤 + 조건 요약 읽기.
- 읽은 날짜 범위: 시작일 + 종료일 + 필요한 명시적 완료 + 요약 읽기.
- 날짜 텍스트 입력: 현재 위젯에서 허용되는 입력/blur 처리를 묶고, 이름이 바뀌는 Done은 실행 직전에 의미 조건으로 다시 찾는다.

중간에 DOM 교체/다른 작업면 전환/불명확한 실행이 생기면 나머지는 중단하고 현재 원문·값·ref를 돌려준다. 자동으로 다음 비슷한 버튼을 누르거나 이미 완료한 입력부터 반복하지 않는다. 이미 요청한 목표와 맞는 새 증거가 있으면 추가 전체 지도 없이 이어간다.

### 우선 4: 짧은 B플랜을 유지한다

1. 실패 이유를 구분한다: 이름/범위 불일치, 아직 미렌더링, native 입력 제약, stale DOM, 실제 가림, 사용자 승인, 사이트 차단은 다르다.
2. 같은 목적을 유지하고 근거를 바꿔 좁게 한 번 재조회한다. 전체 날짜 문자열 변형을 계속 추측하지 않는다.
3. 다시 못 찾으면 실제 이미지를 보고, 이미지와 연결된 ref/구조로 돌아온다. 임의의 n번째 동일 숫자를 선택하지 않는다.
4. 정확한 연결된 target이 `clipped=scroll`이면 기존 자동 scrollIntoView를 우선 활용한다. target이 아직 DOM에 없으면 소유 컨테이너나 관찰한 이동 컨트롤을 사용한다.
5. 실행 결과가 불명이면 적용 상태부터 확인한다. CAPTCHA/접근 제한은 별도 분류하고 다른 조사 사이트로 넘어간다.

이 절차를 긴 경고 목록으로 SKILL에 붙이지 않는다. 구현 시에는 기존 핵심 문장을 교체하고, 예시·근거·제약은 별도 상세 문서에 둬야 한다. 짧은 스킬을 유지해야 한다는 사용자 요구는 그대로 유효하다.
