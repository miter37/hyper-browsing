# 실행 규칙과 일회성 도구

직접 click/fill/select/press, 저장된 선언형 액션, 일회성 batch는 같은 대상 선택·5초 기본 시간제한·오류 분류·변화 보고·입력 확인 규칙을 사용한다. 코드 액션은 `ctx.act(kind, params)`로 같은 경로를 사용할 수 있다. 기존 `ctx.page`는 호환성을 위한 고급 경로이며, 임의의 raw Playwright 코드를 자동으로 이 규칙에 맞춰 바꾸지는 않는다. `ctx.locator()`도 모호한 요소를 거부하고 기본 시간제한을 적용한다.

## 현재 화면의 요소 참조

```text
webctl snapshot --session ID --query Name
webctl fill --session ID --ref e27 --value Alice
webctl press --session ID --ref e27 --key Enter
```

snapshot이 반환한 `ref`는 현재 탭의 실제 DOM 요소에 연결된다. 메인 문서와 열린 Shadow DOM에 적용한다. 목록의 위치가 바뀌어도 같은 요소를 가리킨다. 다른 탭·문서에서 사용할 수 없으며 요소 교체·식별 정보 변경·페이지 이동이면 `stale_ref`를 반환한다. 존재하지 않는 요소를 비슷한 역할·이름·순번의 요소로 대신 누르지 않는다.

일반 속성·입력값·선택 상태 변화만으로 같은 요소의 번호를 새 번호로 재사용하지 않는다. `stale_ref` 또는 변경된 화면을 만나면 새 snapshot을 관찰한다. 참조 번호는 순번이 아니므로 `--nth`, `--within`, 의미 선택자, `--all`과 함께 사용할 수 없다.

참조는 로컬 데몬의 현재 문서 수명에만 유효하다. 이전 캡처 파일의 번호나 같은 화면처럼 보이는 다른 탭의 번호를 사용하지 않는다. 영구 액션은 역할·이름·맥락·조건으로 대상을 다시 찾고 결과를 재검증한다.

## 일회성 배치

```json
{
  "commands": [
    {"op":"fill","ref":"e27","value":"Alice"},
    {"op":"fill","locator":{"label":"City","exact":true},"value":"Seoul"},
    {"op":"select","ref":"e29","option":"Two"}
  ]
}
```

```text
webctl batch --session ID --input-file commands.json
```

최초 버전은 이미 관찰한 입력·선택만 최대 10개, 전체 30초 예산으로 수행한다. 명령 형식은 모든 단계를 실행하기 전에 검증한다. 각 단계의 대상은 실행 직전에 다시 확인한다. `submit`, click, goto, press, eval은 배치에 넣을 수 없다. 입력만으로 저장이 발생하는 사이트는 현재 작업의 승인 범위를 확인해야 한다.

실패·입력값 불일치·모호함·결과 불명·URL/요소 구조/메뉴 변화가 생기면 즉시 중단한다. results에는 완료·중단 단계와 결과를, stoppedAt에는 중단한 0부터 시작하는 단계 번호를 반환한다. 완료된 입력은 남을 수 있고 rollback은 false다. 결과가 불명확한 배치 전체를 다시 보내지 않는다. 현재 화면을 확인한 뒤 남은 작업만 수행한다.

배치는 자산 등록을 하지 않는다. 일회성 입력을 묶었다는 이유만으로 액션·러너를 생성할 필요가 없다. 현재 작업의 최소 구조 관찰은 기존 학습 기록에 남을 수 있다.

## RPC 응답 손실과 중복 요청

execution의 의미:

| 값 | 의미 |
|---|---|
| not_started | 동작 전에 대상·입력·권한이 거부되거나 연결이 거부됨 |
| completed | 도구 호출 완료. 업무 성공은 별도 검증 필요 |
| partial | 배치 일부만 수행됨. 완료한 단계도 확인 필요 |
| outcome_unknown | 이미 실행됐을 수도 있음. 재전송 금지 |

전송 뒤 시간 초과·연결 종료·불완전 응답은 outcome_unknown이다. 타이머는 헤더 수신뿐 아니라 응답 본문 해석까지 포함한다. 빠른 RPC와 일반 CLI는 같은 전송 함수를 사용하며, 전송된 요청을 런처에서 다시 실행하지 않는다. 연결 거부가 확인돼 전송되지 않은 경우만 런처로 넘길 수 있다.

각 요청의 requestId로 실행을 추적한다. 같은 ID·같은 요청은 데몬의 한 실행을 공유하며 다른 내용으로 ID를 재사용하면 거부한다. 같은 세션의 명령과 배치는 순서대로 실행한다.

전송 모듈은 보내기 전에 ID를 만들며 타임아웃·연결 종료 오류 응답에도 `requestId`를 반환한다. CLI 프로세스 자체가 종료되어 ID를 확인할 수 없는 경우에는 현재 화면으로 적용 여부를 확인한다. `running`이면 짧은 간격으로 상태를 다시 조회하되, 기다림을 멈춘 뒤에도 실행 요청을 재전송하지 않는다.

```text
webctl request status --id REQUEST_ID
webctl request status --id REQUEST_ID --verbose
```

실행 중이면 running, 완료했으면 completed와 실제 결과를 반환한다. 이 상태는 업무의 성공을 뜻하지 않는다. 데몬은 최대 512개의 최근 요청을 보관하고 결과 조회는 5분 범위에 한정한다. 데몬 재시작·만료·메모리 한도로 결과가 없으면 unknown이며 페이지에서 적용 여부를 확인한다. 캐시가 없다는 사실은 명령 미실행의 증거가 아니다. ID 조회 자체로 작업을 재실행하지 않는다.

## 간결한 기본 출력

기본 응답에는 실행 상태, 실패 이유, 모호함과 후보, 차단·잘림, effect, 입력 확인, 검증 결과와 requestId를 남긴다. 큰 스냅샷·Playwright 로그·성공한 검증 조건의 반복 출력은 줄인다. 값의 존재만으로 업무 성공을 선언하지 않는다.

저장 액션의 실행이 중단됐다면 사후 조건이 이미 APPLIED여도 해당 버전의 성공·승격 증거로 집계하지 않는다. APPLIED 상태인 쓰기 작업은 다시 실행하지 말고 사용자 요청 결과와 자산 검증 결과를 구분해서 판단한다.

`--verbose`는 전체 효과·검증 상세를 반환한다. snapshot, `--observe`, forms, list, eval 같은 명시적 데이터 요청은 요청한 데이터를 그대로 반환한다. 추가 호출 없이 작업할 수 있을 정도의 기본 관찰 정보를 유지하며, 상세 로그가 필요하면 request status --verbose로 조회한다.

## 유지하는 안전 규칙

headless에서 실행 실패가 확인되면 공유 Chrome의 다른 명령이 끝난 뒤 headed 전환을 한 번 시도한다. 조회·명시적 페이지 이동은 한 번 재시도하며, 쓰기·저장 액션·배치·ref는 새 관찰로 이어간다. 상태 조회는 전환 대기와 분리된다. 자세한 전환·세션 복원 조건은 [브라우저 안내](BROWSER.md)를 따른다.

모호한 대상은 첫 요소로 대체하지 않는다. 실제 조작은 별도 문서의 사용자 승인 범위를 따른다. 쓰기 실패는 APPLIED / NOT_APPLIED / UNKNOWN을 먼저 확인하며, 테스트 목적으로 쓰기 작업을 반복하지 않는다. 기능의 효과는 실행 성공률·잘못된 대상 선택·호출 수·반환 데이터 크기·생성/검증/수정 비용으로 평가한다. 엔진 교체는 측정된 병목이 있을 때 별도로 비교한다.

## 페이지 상태와 새 탭

pageState는 ready/loading/blocked/navigation_error/partial/unknown이다. ready는 과업 성공이 아니다. observation.complete=false는 읽지 못한 부분이 있음을 뜻한다. no_match만으로 headed 전환하지 않으며 환경 실패 증거가 있을 때만 한 번 전환한다.

effect.newSessions는 새 탭의 sessionId·URL·제목·setupStatus를 제공한다. 원래 세션은 그대로이며 사용자가 원하는 대상을 관찰해 다음 세션을 선택한다. 배치·선언형 저장 액션은 새 탭이나 관찰 필요 상태에서 멈춘다.

위험도는 선택한 실제 요소를 고정한 뒤 판정한다. 검색 필터와 실제 구매를 구분하고 CSS·Enter·fill --submit도 결제 확인을 피할 수 없다. 입력값이 기대값과 다르면 제출하지 않는다. [읽기 전용 검증](VERIFICATION.md)을 사용해 결과 조건을 확인한다.

### 공통 입력 간격

클릭·호버·입력·선택·키 누름은 첫 액션을 포함해 매번500~1000ms의 랜덤 지연을 적용한다. 입력 후 Enter 제출, 커스텀 드롭다운 열기 후 옵션 클릭, 안내창 닫기에도 별도의 지연을 적용한다. 화면 준비·변화 확인을 위한 기존 대기는 별도로 유지하므로 실제 전체 간격은 더 길 수 있다. 스냅샷·추출·verify 같은 읽기에는 이 지연을 적용하지 않는다.

지연 뒤 현재 대상을 확인하며, 입력 후 제출은 대기 뒤 입력값과 제출 위험도를 다시 확인한다. 직접 명령·선언형 저장 액션·일회성 배치·ctx.act는 같은 실행 경로를 따른다. 코드 액션에서 ctx.page로 Playwright 조작을 직접 호출하면 공통 계층을 우회하므로 ctx.act를 사용한다. 이 설정을 사이트별 학습 자산으로 저장하지 않는다.
