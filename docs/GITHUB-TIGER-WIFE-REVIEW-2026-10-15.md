## 실제 막힘과 공통 원인

1. **숨겨진 제목이 개요에 섞였다.** S21 `Delete miter37/tiger-wife`는 열리지 않은 대화상자의 제목이었다. section read에서 heading·버튼이 no-box이고 실행 ref가 없었다. 3,450px 스크롤과 지도/개요/동일 섹션 재조회, explain까지 이어졌으나 실제 opener를 얻지 못했다. 마지막에는 P2 controls query로 보이는 Delete this repository ref를 얻어 진전했다. outline 수집은 해당 요소 자신의 computed style만 보고 조상의 display:none 등 비렌더 경계를 충분히 확인하지 않는다. 특정 사이트 문구를 제외하는 해결책은 사용하지 않는다.
2. **비렌더 제목이 섹션 종료 경계에도 영향을 준다.** Danger Zone 레벨2 구역은 숨겨진 레벨1 제목 때문에 일찍 끝나 삭제 opener가 포함되지 않았다. 개요 후보 가시성과 섹션 경계의 제목 판정이 같은 공통 기준을 써야 한다. 뷰포트 밖과 아예 비렌더는 구분해야 한다.
3. **at이 두 fill에서 누락됐다.** 저장소 이름 입력과 최종 삭제 경로 입력에서 관찰한 label/ref를 사용했지만 at을 보내지 않았다. 후자 응답은 새 consumer로 다시 시작해 같은 dialog 전체 재전달을 유발했다. Luna는 fill이 at을 지원하지 않는다고 잘못 보고했다. 실제로 두 CLI 전역 옵션과 server의 primitive prepare는 fill의 at을 지원한다. 스킬의 실제 fill 예시와 도구 문법 안내를 맞출 필요가 있다.
4. **충분한 근거 뒤에도 전체 지도를 다시 요청했다.** 이름 입력 뒤, Star 뒤, 스크롤 뒤에 지도/개요가 반복됐다. 이 모든 호출을 DOM 변경으로 필수였다고 볼 근거는 없다. 메뉴/섹션의 at에서 상위 범위로 돌아가는 경로가 명시적이면 새 지도로 기준을 초기화하는 행동을 줄일 수 있는지도 검토할 가치가 있다.
5. **관찰 완결성과 조회 목적을 구분해야 한다.** no-box 컨트롤과 숨겨진 본문이 section read에 나오지만 실행 ref는 없는 상태였다. coverage.complete=true여도 실행 가능한 영역이라는 뜻은 아니다. 이미 비렌더 근거가 있으면 스크롤이나 큰 explain을 기본 복구로 선택하지 않도록 UI 지식을 보강해야 한다.

## 다음 개선의 우선순위

첫째는 outline과 섹션 경계에 공통 비렌더 판정을 적용하는 것이다. 조상 display:none/hidden 등 실제 DOM/CSS 근거를 보존하고 뷰포트 밖 정상 제목은 유지한다. 둘째는 fill/select/press까지 at을 이어 쓰는 스킬 예시와 명령 안내를 명확히 한다. 셋째는 무의미한 전체 지도 초기화와 동일 no-box 범위 반복을 줄인다. 마지막으로 실제 사용자 흐름의 총 시간·출력·호출과 개입을 함께 평가한다.

이 문서는 분석이며 코드 수정이나 후속 재실험을 수행했다는 뜻이 아니다. 원격 저장소 작업은 이 한 번으로 종료했다.
