# 목표 동반 검색 실전 전략

작성: 2026-10-15 · GPT-6 Codex

상태: 헤드리스 실전에서 얻은 전략 초안. `.runtime`의 임시 스크립트로 탐색했다. 정식 API나 기본 스킬 계약으로 승격한 문서가 아니다. 제품 코드·엔진의 사이트별 예외를 추가하지 않았다.

## 본질적인 목표

목표는 검색 함수를 빠르게 만드는 데 그치지 않는다. 사람이 한 번의 인지로 처리하는 작업을 LLM이 여러 번의 관찰·판단·명령 생성으로 나눠 수행하는 비용을 줄이는 것이다. 사람이 UI를 사용할 때는 현재 단계, 실제 선택지, 입력·선택·제출의 차이, 실행 결과가 한 화면에 이어진다. 현재 프로토콜은 그 연결을 여러 호출과 문자열 재구성에 분산한다.

LLM은 목표·선택 기준·예외를 판단하고, 이미 지정된 작은 절차의 목표 탐색·대기·대상 해소·실행·확인은 로컬에서 이어갈 수 있어야 한다. 이는 사이트별 영구 러너를 늘리거나, 관찰하지 않은 대상을 추측해 자동 클릭하는 정책이 아니다.

## 실전에서 확인한 사실

### Wikipedia

Apollo 11에서 Crew를 넓게 검색하면 crewed mission 등까지 17개가 걸렸다. 정확한 Prime crew 제목으로 좁혀 표만 읽었고 Command Module Pilot이 Michael Collins임을 확인했다. 역할·이름에 within=Command Module Pilot을 붙인 클릭은 no_match였다. 표에서 실제로 확인한 문서 URL로 이동해 인물 문서를 확인했다.

검색 결과의 표시 이름과 실행기의 대상 해소 규칙이 같다는 보장이 없으면, 정보를 찾고도 다시 실행 대상을 찾는 비용이 생긴다. 이는 더 많은 주변 문구를 붙이는 것으로만 해결되지 않는다.

### MDN

홈의 검색 버튼은 열린 Shadow DOM 안에 있어 임시 document.querySelectorAll 검색에서 빠졌다. 일반적인 열린 shadow 순회를 추가한 뒤 찾았다. 검색창 열기와 Search 입력칸 찾기, Array.prototype.map 입력과 자동완성 후보 찾기, 정확한 option 선택과 문서 제목 확인이 각각 함께 진행됐다.

문서 페이지에서는 같은 검색 UI가 글자 대신 아이콘과 title="Search the site"로 표현돼 있었다. 임시 이름 계산에서 title과 공백 처리를 빠뜨려 다시 0건이 됐다. 일반적인 이름 후보 처리를 보완한 후 아래의 짧은 계획이 성공했다.

이 두 문제는 정식 HB가 이미 다루는 기능을 임시 검색기에서 별도로 작성하면서 놓친 사례다. 정식 도입 시에는 기존 수집·이름 근거·참조 계층을 공유해야 한다. 별도 저품질 DOM 수집기를 빠르다는 이유로 기본 경로에 놓으면 기능이 퇴행한다.

### Open Library

검색창을 열고 astronomy를 입력한 뒤 읽기 가능만 필터를 켰다. 스위치의 표시 이름에 결과 수가 붙어 앞서 받은 이름의 정확 일치가 실패했다. 필터 클릭 자체는 성공했지만 다음 제출 버튼의 정확 일치는 실패했다. 제출 버튼 불일치의 상세 원인은 확정하지 않았다. 검색창 Enter로 검색을 제출했고 has_fulltext=true를 확인했다. 정렬 메뉴의 최신순을 선택해 sort=new를 확인했다. 이를 출판연도 최신순이라고 추가 해석하지 않았다.

메뉴의 실제 역할은 menuitemradio였으나 검색 조건에서 menuitem만 요청해 목표 결과는 비었다. 조작 효과에는 실제 역할과 최신순 문구가 이미 있었으므로 이를 사용해 진행했다. 잘못된 역할 제한이 추가 조회를 만들 수 있다.

내가 최신순을 일본어 한자로 잘못 다시 입력해 약 5.8초의 no_match를 추가한 실수도 있었다. 앱 결함으로 집계하지 않는다. 실제 대상을 다시 문자열로 작성하는 과정 자체가 오류 경로임을 보여준다.

도서 결과 두 개를 확인한 뒤 상세 링크를 열자 사람 확인 페이지로 이동했다. 검색·필터·정렬 성공과 상세 접근 차단을 분리한다. 인증 우회나 headed 재전환을 하지 않았다.

## 시간과 비용에서 확인한 것

첫 세 사이트 구간은 스크립트 호출 22회, 내부 RPC 40회, 공개 출력 19,857B였다. 스크립트 실행시간 합계는 49.454초, 첫 시작부터 마지막 종료까지는 462.224초였다. 나머지 시간을 전부 LLM 사고시간이라고 부를 수는 없다. 임시 코드 보완, 로그 확인, 도구 간 지연과 사용자 메시지를 포함한다. 다만 이 수행에서 수 ms의 검색 자체가 전체 지연을 지배한 것은 아니다.

| 사이트 | 스크립트 호출 | 내부 RPC | 공개 출력 | 스크립트 시간 합 |
|---|---:|---:|---:|---:|
| Wikipedia | 4 | 7 | 3,187B | 5.268초 |
| MDN | 6 | 11 | 6,524B | 6.082초 |
| Open Library | 12 | 22 | 10,146B | 38.104초 |

이후 MDN에서 단일 로컬 계획을 시도했다. 계획은 검색 버튼 찾기 → 검색창 열고 입력칸 찾기 → Array.prototype.filter 입력과 정확한 후보 찾기 → 후보 선택과 문서 제목 확인이었다. 각 목표가 정확히 하나일 때만 그때 관찰한 역할·이름으로 기존 실행기를 호출한다. 0개·여러 개·오류·불명 결과에서는 정지한다.

검색 버튼 이름을 놓친 초기 두 시도는 각각 약 1.2초에 정지했다. title 처리 보완 뒤 성공한 계획은 6.102초, 내부 RPC 7회였다. 중간에 LLM이 다음 명령을 작성하지 않았다. 계획 작성·보완 시간을 제외한 성공 실행 수치이며, 이전 수행과 통제된 A/B 실험이 아니다. 원시 `.runtime/goal-plan-log.jsonl`과 `.runtime/goal-follow-log.jsonl`을 보존한다.

## 우선순위가 높은 병목

1. **작업 단위의 분절:** 한 번의 UI 조작마다 LLM을 다시 깨워 다음 명령을 만들게 한다. 설명 발화만 없애도 이 왕복은 남는다.
2. **관찰과 실행 대상의 불일치:** DOM에서 만든 이름을 다시 getByRole 문자열로 해석하면 shadow, title, 동적 숫자, 이름 출처 차이 때문에 이미 찾은 대상을 놓친다.
3. **상태 전환의 단절:** 입력 후 지연 후보, 포털 영역, loading과 진짜 0건을 현재 단계의 일부로 추적하지 못한다.
4. **조회 조건의 과도한 부담:** LLM이 패널·핸들·필드·정확한 ARIA 하위 역할을 모두 맞혀야 진전한다.
5. **실패의 비싼 확인:** 이미 대상이 맞지 않는 실패에 반복적인 5초 기다림과 별도 진단 요청이 붙는다.

## 실전 전략의 방향

- 목표는 단어뿐 아니라 확인할 결과를 포함한다. 예: 특정 문서 후보 선택 후 제목이 정확히 일치해야 완료다. 의미 판단이나 안전성은 검색어 일치로 대신하지 않는다.
- 같은 기본 수집·이름 근거·실행 ref를 검색과 조작에서 공유한다. 찾은 요소를 다시 문자열로 재발견하도록 강제하지 않는다. 옛 ref를 다른 대상으로 재할당하거나 guard를 약화하지 않는다.
- 목표 검색은 기존 조작 결과를 보완한다. 검색 결과가 0이어도 effect에 다음 선택지가 이미 있으면 같은 내용을 다시 묻지 않는다.
- 역할을 너무 세세하게 지정해야만 찾는 인터페이스를 피한다. 정확한 역할을 모를 때는 조작 가능한 후보 안에서 조회하고 실제 역할을 반환한다. 실행 시에는 실제 참조와 공통 모호함 검사를 사용한다.
- 2~4개의 짧고 검증 가능한 절차를 임시 계획으로 묶는다. 각 단계에서 새 후보를 확인하고, 미리 지정한 조건이 유일하게 맞을 때만 진행한다. 고정된 옛 문자열을 순서대로 클릭하는 배치로 구현하지 않는다.
- 실패하더라도 읽기 전용 목표 조회와 원래 실행 결과를 함께 반환할 수 있다. 다음 조작은 중지한다. 완료된 앞 단계와 실행되지 않은 뒤 단계를 분리한다.
- 잘못된 범위에서 0건을 반복하지 않는다. 실제로 새로 열린 영역을 연결하고, 범위 밖·비렌더·부분 수집·지연·진짜 불일치를 구분한다. 모르면 현재 판단에 필요한 작은 범위만 넓힌다.
- 캡션·검색어·실제 값·적용 상태를 구분한다. 숫자를 무조건 이름에서 제거하지 않는다. 수량이 바뀌면 동작 의미도 바뀔 수 있다.
- 소속은 명시 연결이나 실제 조상으로 전달한다. 포털 메뉴에 무관한 앞쪽 footer 제목을 붙이는 식의 파생 맥락은 기본으로 쓰지 않는다.
- 기존 0.5~1초 입력 간격, 실행 결과 불명 시 중복 실행 금지, 사용자 승인·참조 수명·차단 처리 원칙은 그대로 유지한다.

## 정식 도입 전 남은 확인

목표 검색만 추가한 조건과 짧은 계획까지 사용한 조건을 같은 과업에서 비교해야 한다. 모델에게 준 출력만 아니라 입력, 모델 호출 횟수, 실제 도구 시간, 사용자 개입, 실패·복구 시간을 함께 기록한다. 계획의 0개/복수 후보/지연/문서 교체/예상 밖 팝업/불명 실행에서 실제로 멈추는지 확인해야 한다. 이번 성공한 검색 문서 계획만으로 쓰기·예약·삭제 같은 절차를 자동화하도록 확대하지 않는다.

## 추가 검증과 예외 전략

추가 5개 사이트의 결과, 확신의 범위, 실패 시 B플랜과 정식 통합 순서는 [목표 계획 검증 기록](GOAL-PLAN-VALIDATION-2026-10-15.md)에 정리했다. 방향의 채택과 전면 구현 완료는 구분한다.
