## 과업과 환경

사용자 요청에 따라 루트 에이전트가 프로젝트의 SKILL.md와 launcher를 사용했다. dy1의 기존 headed Chrome과 restored_fcf95e30 탭을 재사용했다. 별도 브라우저나 설치된 스킬 사본을 사용하지 않았다. 학습·자산화, 예약·결제는 하지 않았다.

스스로 설정한 과업: 2026-11-15 인천→다낭, 11-19 귀국, 성인 1명/이코노미/직항의 저렴한 왕복 후보 3개와 수하물 확인. 한국어 Booking 메인의 항공권 메뉴가 제휴 KAYAK로 연결돼, 과거 사용했던 flights.booking.com 진입점을 사용했다.

## 과정 분석

1. 출발지 서울 모든 공항의 선택 칩을 제거하고 ICN만 선택했다. 제거 버튼은 실제 로컬 폼 편집이지만 공통 위험 엔진이 irreversible로 분류했다. 관찰 후 해당 동작에만 confirm을 사용했다. 사이트 예외는 추가하지 않았다.
2. ICN 조회를 name 필드로만 제한하자 0건이었다. 실제 option은 이름 없이 text에 ICN이 있었다. name/text로 보완해 찾았다. 초기 역할/필드 추측은 모델 운영 오류다.
3. ICN option 클릭 후 그 노드가 사라졌다. selected=true라는 같은 노드 검증은 target_replaced로 멈췄다. 선택을 반복하지 않고 외부 버튼의 ICN 표시로 확인했다. DAD 선택에는 같은 형태의 바깥 표시 검증을 사용해 통과했다.
4. 도착지 입력은 role=combobox지만 확인한 name/placeholder가 비어 있었다. 목표 검색은 비어 있지 않은 terms가 필수여서 조회가 막혔다. 패널 read도 포털 입력을 포함하지 않았다. 작은 읽기 전용 eval로 현재 보이는 input을 확인한 뒤 관찰한 input[role=combobox] 선택자로 채웠다. 이름 없는 컨트롤과 포털 범위를 위한 일반적 복구 동선이 필요하다.
5. 날짜 2개를 run 한 호출로 선택했고, 직항 체크와 검색도 한 호출로 완료했다. 작은 결정적 구간 묶기의 실사용 이점이다.
6. run 마지막 follow가 복수 후보를 반환하면 remaining=0이고 모든 동작을 끝냈어도 partial/follow_ambiguous로 나왔다. 다음 행동 전 대상을 고르는 모호함과, 마지막 읽기에서 여러 결과를 요청한 상황을 구별해야 한다.
7. 메뉴/날짜 열기 직후 follow는 즉시 조회라 새 UI가 뜨기 전에 본문을 반환했다. 상태 전이 확인과 후속 조회를 묶는 일반 계약이 필요하다. 무조건 긴 sleep이 답은 아니다.
8. 결과 전환 중 사라진 alertdialog 패널을 read하자 outcome_unknown이 나왔다. 읽기 대상 만료와 쓰기 적용 여부 불명은 구별하는 편이 정확하다.
9. 자세히 보기 후 수하물 introduced 검증에는 실제 일치가 여러 개 있었다. 반환은 ambiguous였고 3초 뒤 unconfirmed가 됐다. 존재 검증과 유일한 실행 대상 검증을 같은 기준으로 처리하는 한계가 드러났다. 원인 코드는 이 실험에서 추가 조사하지 않았다.
10. 상세 창 content read는 짧은 구분자 텍스트와 aria-hidden 중복까지 60행을 반환했지만 수하물 끝은 다음 페이지로 넘겼다. 현재 창 innerText를 3,200자로 제한한 읽기가 더 간단했다. 원문 순서/항목 소속은 유지하면서 불필요한 구조·공백을 줄이는 일반 읽기 투영이 필요하다.
11. 세 번째 상세 창 goal의 text가 KR에서 끊겼지만 그 후보에는 textTruncated가 없었다. 전달 문자열 잘림의 표식을 모든 경로에서 점검해야 한다.

## 측정과 해석

프로젝트 CLI 40호출: goto 2, find 11, click 10, fill 2, run 4, snapshot 2, read 4, eval 5. run 안의 행동은 별도 단계이므로 40을 UI 동작 수로 부르지 않는다.

CLI 소요 합계 60.469초, 처음~마지막 호출 벽시계 584.674초, stdout 100,169바이트. stdout에는 반복 URL·검증 finding과 follow finding의 중복도 포함한다. 토큰 측정은 하지 않았다. 벽시계는 모델 판단·파일 작성·도구 사이 간격과 앞선 문맥 전환을 포함하며 순수 사이트 응답 시간으로 해석하지 않는다. raw는 .runtime/booking-goal-core-commands.jsonl에 있다.

현재 목표 코어는 연속 조작에서 작동했지만 전체 실험은 아직 빠르지 않았다. 모델의 범위/필드/후조건 선택 오류와 읽기 투영, 즉시 follow의 타이밍이 왕복을 늘렸다. 기존 방식과 동일 조건 대조가 없으므로 전체 속도 개선을 주장하지 않는다.

## 다음 개선 우선순위

1. 마지막 follow의 복수 읽기 결과를 실행 실패로 처리하지 않기. 존재 검증과 유일 대상 검증을 분리 검토하기.
2. 스킬에 지속 컨트롤/외부 표시를 이용한 선택 후 검증과, 이름 없는 입력·포털의 좁은 복구 절차를 명시하기.
3. goal 결과에서 소속 카드의 짧은 식별 문맥을 제공하기. 현재 Details 후보는 owner=listitem만 있어 카드 선택에 부족하다. 전역 본문 추가는 피한다.
4. 좁은 본문 읽기를 원문 순서·소속을 보존한 짧은 출력으로 만들고 잘림 표시를 일관되게 적용하기.
5. expect/follow 중복 finding·긴 URL 반복을 줄이고, 로컬 입력 제거에 대한 공통 위험 분류의 사실 근거를 검토하기.

이 실험은 코드 수정 없이 관찰과 보고로 끝냈다. Booking 이름·URL·CSS를 제품 규칙에 넣지 않았다. 실험용 관찰 선택자는 영구 자산으로 저장하지 않았다.
