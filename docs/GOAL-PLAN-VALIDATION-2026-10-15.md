# 목표 동반 검색과 짧은 조건부 계획: 검증과 B플랜

작성: 2026-10-15 16:02 +09:00 — GPT-6 Codex

## 결론과 확신의 범위

기본 흐름을 `현재 목표 → 조작과 목표 조회 → 확정 가능한 짧은 단계 실행 → 예외만 LLM 판단`으로 발전시키는 데 찬성한다. 단순한 검색 속도보다 매 클릭마다 발생하는 모델의 다음 명령 작성과 관찰 왕복을 줄이는 것이 핵심이다. 기존 HB 수집기·실행기·참조를 대체하는 별도 브라우저 구현에는 찬성하지 않는다. 이번 임시 검색기의 능력 누락과 대상 재해석 문제가 그 이유다.

짧은 검색·문서 탐색에서 작동 가능성을 확인했다. 전체 과업 시간의 개선 폭, 예약·쓰기 작업의 자동 진행, 모든 UI에서의 효과는 검증하지 않았다. 성공 실행의 짧은 시간만으로 전체 준비·수정·복구 비용까지 개선됐다고 주장하지 않는다. 새 문법을 항상 출력하는 방식으로 돌아가지 않는다.

## 관찰 결과

프로젝트 RPC와 공통 실행 계층을 사용했다. 임시 도구는 `.runtime/goal-follow.mjs`, `.runtime/goal-plan.mjs`다. 영구 사이트 자산화·학습 없이 수행했다. 앞선 Wikipedia·MDN·Open Library 이후 아래 다섯 사이트를 추가했다. 따라서 이번 탐색은 합계 8개 사이트다.

IKEA의 마지막 상품 읽기는 검색 결과에 문구와 상품 링크가 존재함을 확인한 수준이다. 상세 정보 비교나 추천 완료로 집계하지 않는다. 검색어가 책상이어도 펜꽂이 같은 관련 상품이 나타났으므로 검색 결과 일치와 사용자 목적 충족을 구분해야 한다.

## B플랜: 다음 단계만 중지하고 필요한 근거만 반환

| 상황 | 우선 처리 | 다음 선택 |
|---|---|---|
| 후보 0개 | 현재 scope·수집 범위·loading·차단·새 영역 여부와 기존 effect를 함께 확인 | 지연 근거가 있으면 제한 대기. 범위가 틀렸으면 한 단계 넓히거나 열린 영역만 조회 |
| 후보 여러 개 | 소속·역할·목적지·상태가 붙은 소수 후보 반환 | LLM이 대상을 선택하거나 조건을 좁힌 뒤 해당 ref로 실행. 첫 후보 자동 실행 금지 |
| 찾았지만 실행 시 모호함/오래된 ref | 실행 중지, 대상 연결 상태 확인 | 필요한 영역에서 새 ref를 얻음. 문자열 정규화나 same-href 첫 선택으로 회피하지 않음 |
| 예상 밖 대화상자·팝업 | 새 영역 안에서 목표 조회 | 확인한 선택지만 처리하고 원래 목표로 복귀. 가려진 본문을 무조건 재조회하지 않음 |
| 실행 완료, 기대 상태 미확인 | execution·ok·필드 변화·적용 상태 분리 | 필요한 값/URL/목록 변화만 추가 확인. 체크됐다는 이유로 목록 적용 성공 선언 금지 |
| 실행 결과 불명 | 이후 조작 중지 | 적용 여부부터 읽어 확인. 앞 단계부터 재실행 금지 |
| CAPTCHA·접근 제한 | 차단 사실과 완료된 범위 보고 | 테스트 모드 유지, 우회하지 않음 |
| 작은 범위 정보로 판단이 계속 안 됨 | 관련 패널만 상세 맥락/관계 출력 | 이때 HWM 상세를 사용. 전체 그래프나 전체 본문부터 보내지 않음 |

기본 예외 처리 한 번으로 해결되지 않으면 같은 조회를 반복하지 않고 짧은 원인·후보를 LLM에 반환한다. 이 횟수는 운영 시작값이며 고정된 최적값으로 주장하지 않는다. 위험한 조작은 원래 승인·확인 경계를 넘지 않는다.

## 실전에서 얻은 일반 노하우

1. 목표는 단어가 아니라 대상 조건과 완료 근거를 포함해야 한다. `정렬`→`낮은 가격 라디오`→`checked=true`→`적용 URL/목록`은 서로 다른 단계다.
2. 동의어를 많이 넣는 것보다 현재 상호작용 범위가 중요하다. IKEA 쿠키 창에서 전역 `저장` 검색은 뒤쪽 쇼핑 목록 버튼을 대량 반환했다. 실제 dialog 조상으로 좁히자 필요한 쿠키 컨트롤이 나왔다.
3. 유일 후보도 목적이 맞다는 보장은 없다. IKEA에서 유일한 `닫기`는 배송 안내 닫기였다. effect의 사라진 내용으로 확인했으며 정렬창 닫기 성공으로 집계하지 않는다. 소속과 기대 변화가 필요하다.
4. 새 후보가 하나 나왔다고 로딩이 끝난 것은 아니다. 정렬 클릭 직후와 다음 조회 사이에 URL과 목록이 바뀌었다. 기다림은 고정 긴 sleep보다 관련 상태의 제한 관찰이어야 한다.
5. 중복 검색창·동일 이름 링크는 흔하다. Python과 HN의 중복은 예외 사이트 문제가 아니다. 목적지와 소속을 보존하고 실행 ref를 공유해야 한다.
6. 역할을 모를 때 과도한 role 제한으로 0을 만들지 않는다. 검색칸이 searchbox일 수도 combobox일 수도 있다. 실제 반환 역할을 사용한다.
7. 임시 계획은 2~4개 정도의 검증 가능한 작은 단계로 시작한다. 다음 대상이 유일하고 필요한 상태가 맞을 때만 계속한다. 이는 성공 이력을 저장하는 사이트 러너와 다르다.
8. LLM은 시작할 목표·선택 조건·중단 조건을 선언하고, 실행 중 설명 발화 대신 도구 호출에 집중한다. 필요한 사용자 질문이나 최종 보고는 유지한다.

## 정식 통합 순서

1. **대상 연결부터:** 기존 HB 관찰·이름 근거·참조 발급을 목표 조회와 공유한다. 별도 DOM walker를 제품화하지 않는다. 조회가 반환한 실제 ref를 공통 실행기로 넘긴다.
2. **조작+조회 계약:** 기존 결과의 실행 불명·차단·후보·변화·확인 요구를 보존하고 목표 조회를 함께 반환한다. 0개도 범위와 수집 상태를 명시한다.
3. **작은 조건부 계획:** 목표 유일성·필드·문서/URL 변화 등의 명시 조건만 평가한다. 실패 시 완료/미실행 단계를 나누며 맹목 재시도하지 않는다.
4. **SKILL과 동시 변경:** 현재 단계 목표, 새 영역 scope, 예외 시 작은 확대, 최근 정보 재요청 금지, 위험 경계와 중단 조건을 도구 계약과 동일하게 안내한다.
5. **같은 과업 전체 비용 비교:** 최종 요약 크기가 아닌 추가 조회·모델 입력/출력·도구 시간·복구·모델 왕복을 함께 측정한다. 작은 읽기/검색 과업부터 적용한다.

## 모드 정책과 구현 한계

이번 npm 최초 시도에서 기존 자동 headless→headed 폴백이 실험 조건을 바꿨다. 이를 제외하고 headless로 복구한 뒤 요청별 `allowHeadedFallback:false` 가드를 서버에 추가해 이후 요청에 전달했다. 기본 폴백 동작은 유지한다. 마지막 browser status에서 headless=true를 확인했다. 실험 모드 정책은 실패 복구 경로에도 전파되어야 한다.

임시 검색기는 브라우저 계산 accessible-name의 완전한 구현이 아니며 ref를 발급하지 않는다. 문서와 열린 shadow를 검색하고 viewport 여부를 따로 표시한다. 이 한계가 남은 상태에서 전면 제품 전환 완료라고 보고하지 않는다. 이번에는 검증·정리와 위 모드 가드만 추가했으며 정식 통합 전체는 아직 수행하지 않았다.

원시 입력·RPC·공개 출력과 계획 결과는 로컬 `.runtime/goal-follow-log.jsonl`, `.runtime/goal-plan-log.jsonl`에 남겼다. 민감한 브라우저 세션 데이터가 섞일 수 있으므로 공유 자산으로 자동 올리지 않는다.

## 사용자 추가 요청: Airbnb·Google Maps

두 사이트 모두 headless로 수행했고 마지막 browser status에서도 확인했다. 사이트별 한 탐색 흐름이며 통제 비교나 반복 측정이 아니다. 사용자 중단·재개, 진단, 로그 확인을 포함한 벽시계 시간과 아래 도구 시간은 다르다.

| 사이트 | 실제 확인 | 로컬 짧은 계획 | 실패·복구 |
|---|---|---|---|
| Airbnb | 종로구 자동완성 선택, 2026-10-25~27, 최고 요금 300000 입력 및 적용. 최종 URL의 checkin/checkout/price_max 확인 | 체크아웃 선택→검색→필터 발견 4.175초/5RPC | 임시 이름 중복으로 no_match. 기존 HB read의 정확한 이름으로 복구. 필터 적용 링크는 external_write로 막혀 목적지가 검색 URL임을 읽고 confirmed로 실행 |
| Google Maps | 서울 종로 카페 검색, Rating 메뉴의 4.5 항목 ref 실행, 목록 갱신 후 Corcovado 상세 제목·주소·전화 확인 | 검색 입력→제출→필터 후보 반환 4.206초/5RPC, 후보2개로 정지 | 보이는 4.5는 aria-hidden 하위 문구여서 accessible-name 클릭 실패. 메뉴 내부 문구·상자와 발급 ref를 연결해 복구. 필터 직후 옛 목록의 Respirer 클릭 실패 후 새 목록에서 Corcovado 선택 |

Airbnb에서 가격 필터를 입력했다고 실제 모든 카드가 30만원 이하라고 단정하지 않았다. 적용 직후 본문에는 옛 목록이 남았고, 요금의 기준도 이 테스트에서 확정하지 않았다. Maps도 광고 카드에 4.4가 남았으므로 평점 항목 선택이 모든 표시 결과를 4.5 이상으로 보장한다고 답하지 않는다. 장소 상세의 주소는 `86-1 Supyo-ro, Jongno District, Seoul`, 전화는 `02-2272-0111`로 확인했다. 전체 main에서 얻은 별점 목록은 다른 카드도 포함하므로 장소 상세 평점의 근거로 쓰지 않았다.

측정 범위: goal-follow 로그 기준 Airbnb는 15회 스크립트/31RPC/조작시도10회(실패2)/도구시간합23.799초/공개출력22,378B다. 여기에 별도로 기존 HB snapshot/read 2회가 더 있다. Maps는 12회 스크립트/27RPC/조작시도7회(실패2)/도구시간합22.158초/공개출력14,154B이며 기존 HB snapshot/read/read-repeat 3회가 더 있다. 계획이 내부 호출한 스크립트도 이 합계에 이미 들어가므로 중복 가산하지 않는다. 바이트는 goal-follow 공개 출력만이고 별도 CLI·계획 최종 요약·모델 입력은 포함하지 않아 전체 토큰 비용으로 쓰지 않는다.

추가 노하우:

- **보이는 문구와 접근 가능한 이름은 다르다.** 숨김 문구를 name으로 승격하지 않는다. visible text·실제 소속·발급 ref를 함께 제공해야 한다. Airbnb 중복 이름과 Maps 이름 없는 평점 항목이 서로 다른 방향의 사례다.
- **행동 후 조회는 오래된 성공 근거를 피해야 한다.** URL 변경만이 아니라 결과 영역 갱신·busy·목표 노드 유효성을 확인해야 한다. 즉시 하나라도 매치되면 대기를 끝내는 임시 구현은 개선 대상이다.
- **소속 없는 전역 검색은 팝업 뒤의 본문을 섞는다.** Airbnb 필터 안 요금 조회는 전체 문서에서35건, dialog로 좁힌 필드 조회는4건이었다. 실제 열린 영역을 우선해야 한다.
- **결과에는 button뿐 아니라 link도 있다.** Airbnb 적용은 link였다. 역할을 미리 좁히기보다 관찰 역할과 ref를 사용한다.
- **조건 변경은 이전 후보를 무효화할 수 있다.** 새 목록을 확인한 뒤 실행하고 실패한 옛 이름을 반복하지 않는다.
- **정보량 확대 자체는 해법이 아니다.** Maps 메뉴 범위에서도 별 모양 list/item이 다수 출력됐다. 내용과 실제 실행 대상의 연결을 우선하고 장식 구조를 기본 출력에 늘리지 않는다.

방향에 대한 결론은 유지한다. 짧은 확정 단계의 로컬 실행은 유용하지만, 별도 DOM 이름 검색기를 그대로 제품화하면 기존 HB보다 못해지는 구간이 생긴다. 공유 수집·실행 ref·새 영역 scope·상태 전환 완료 조건이 정식 통합의 선행 조건이다. 이번 추가 테스트에서는 제품 코드나 사이트 전용 규칙을 수정하지 않았다.
